# 2026-10-23 — 도구 접근 제어·화면 정보 표시 분리와 도구별 세부 조정

## 목표

관리자 화면 인프라 탭의 두 카드(도구 접근 제어, 그룹별 화면 정보 표시)가 서로의 역할을 침범하고 항목 이름이 실제 동작과 달라 정리한다. 도구 접근 제어는 실행 여부만, 화면 정보 표시는 표시 여부만 담당하게 하고, 특정 도구만 다르게 표시하는 기능을 추가한다. PR 백엔드 #186, 웹 #107.

## 수행한 작업

1. **현황 분석.** 화면 표시 항목 5개가 실제로 무엇을 가리는지 코드로 확인했다. 도구 실행 권한이 결과 표시까지 정하고(`can_see_tool_output = has_tool_access(...)`), 도구 이름과 에러 내용이 다른 항목으로 새며, "호출 메시지"는 사실상 스트리밍 설정이고(지금 모델은 도구 호출 때 문장을 쓰지 않음), "메모리 결과"는 도구 하나 전용이었다.
2. **개선안 작성.** [[decisions/052-tool-access-vs-ui-display-separation|ADR-052]]로 정리했다(처음엔 050번으로 만들어 기존 ADR과 번호가 겹쳐 052로 바꿈).
3. **PR 1 — 역할 분리와 항목 정리.**
   - 표시 판정 5곳을 `_can_show` 하나로 합치고 실행 권한 판정을 뺐다.
   - 결과 화면(`tool_result`) 항목을 추가했다.
   - 에러 상세를 끄면 실행 카드도 "도구 실패"만 남게 했다.
   - 질문 확인 카드는 항상 표시하게 했다(`always_visible_result_tools`).
   - 새 항목 권한은 첫 기동 때 표식으로 한 번만 넣고, 새 그룹에도 기본 권한을 준다.
   - 대화를 다시 열 때도 답변 스트리밍 권한을 적용한다.
   - 실행 카드·실행 인자 분리는 구현 후 논의 끝에 되돌려 "실행 상세" 하나로 두었다.
4. **메모리 결과 통합.** 사례 검색 도구 안의 권한 분기를 없애고 항상 카드를 만들게 했다. 보일지는 결과 화면이 정한다. 옛 키는 기동 시 설정 파일과 DB에서 지운다.
5. **PR 2 — 도구별 세부 조정.**
   - 백엔드: `tool_display_overrides` 테이블, 조회·저장 API, 적용 대기 연동, `can_user_see` 판정을 추가했다.
   - 화면: 버튼과 팝업(드롭다운, 기본값 → 표시 → 숨김 3단계 칸, 예외 수, 저장 안 한 변경 점, 질문 카드 잠금)을 만들었다.
   - 사례 저장 결과를 카드로 바꿨다.
6. **화면 다듬기.**
   - 버튼을 표 위로 옮기고 카드 순서를 감사 → 도구 접근 제어 → 화면 정보 표시 → 비용 예측기로 바꿨다.
   - 항목 설명은 ⓘ 툴팁으로 넣고 말투를 다듬었다(줄바꿈이 어색하던 `text-balance` 대신 일반 줄바꿈).
   - 화면 정보 표시에도 신규 그룹 기본 열을 넣었다(진행 단계·결과 화면 기본 켜짐).
   - 예외 글자를 primary 색으로 바꾸고, 마우스를 올리면 기본색이 되게 했다.
   - 권한 표의 그룹 순서를 그룹 탭과 통일했다(`GROUP_LIST_ORDER`).
7. **시스템 프롬프트 정리.**
   - 기반 프롬프트를 처음 한 번만 만들어 도구를 켜고 꺼도 옛 도구 목록이 남던 문제를 도구 구성별 캐시로 고쳤다. 오늘 로그 71건 중 64건이 옛 목록이었다.
   - 파이프라인 안내를 "단계 → 필요한 도구" 표(`_PIPELINE_STEPS`)로 바꿔, 꺼진 도구의 안내가 남지 않게 했다.
   - 골든 스냅샷은 운영 도구 구성(6개)으로 다시 만들어 운영 프롬프트가 바뀌지 않았음을 테스트로 고정했다.
8. **메모리 도구.** 켜도 호출되지 않던 사례 검색·저장을 살렸다.
   - 원인은 두 가지였다. 프롬프트 캐시 때문에 안내가 빠져 있었고, `vector_search` 필수 지시가 메모리 도구를 밀어냈다.
   - 검색은 STEP 0으로 넣었다.
   - 저장은 강제나 자동 저장 대신 도구 설명을 구체화했다. 성공한 SQL이 올바른 형식으로 저장되는 것을 확인했다.
9. **문서.**
   - 관리자 매뉴얼에 두 카드 설명을 추가했다.
   - 설계 문서 3개(`server-settings-design.md`, `settings-ui-design.md`, 웹 `admin-design.md`)를 실제 화면과 `ApplyMode` 기준으로 정리했다(Visualization 탭 삭제, 파운데이션 = LLM 연결, 라이센스 탭 추가 등).

## 핵심 결정

- **실행과 표시 분리, 공통 기본값 + 도구별 예외.** → [[decisions/052-tool-access-vs-ui-display-separation|ADR-052]]
- **예외는 별도 테이블.** `group_permissions`는 "행 있음 = 허용"이라 "예외로 숨김"을 표현할 수 없다.
- **새 항목 권한은 표식으로 한 번만 부여.** 행이 없으면 넣는 방식은 관리자가 전부 해제한 설정을 재시작마다 되살린다. → [[knowledge/patterns/one-time-permission-seed-marker]]
- **처리 과정 블록 안 결과 카드도 결과 화면이 정한다.** 위치 기준으로 스위치를 나누는 안은 규칙이 늘어서 버렸다.
- **메모리 저장은 도구 설명만 구체화.** 코드 자동 저장, 👍 연동, 강제 문구는 모두 버렸다.

## 배운 것

- 실패한 LLM 요청은 로그에서 복원해 같은 조건으로 다시 보내고, 요소를 하나씩 빼며 원인을 좁힐 수 있다. 상관관계만 보고 "메모리 안내 탓"이라고 추정했는데, 재현해 보니 진짜 원인은 `describe_schema` 호출 문장 예시였다. → [[knowledge/troubleshooting/llm-behavior-replay-ablation]]
- 모델은 프롬프트와 도구 설명의 호출 문장 예시(`describe_schema(group="…")`)를 실제 도구 호출 형식으로 베낀다. → [[knowledge/prompting/llm-copies-template-placeholders]] 사례 추가
- 운영 설정을 기본값과 합쳐 읽지 않는 구조에서는, 새 키를 기본값 파일에 추가해도 운영 환경에 저절로 생기지 않는다. 표식 장치로 운영 설정에 넣어 줘야 한다.

## 문제 & 해결

- **문제:** `describe_schema` 호출이 `Tool 'describe_schema(search="작전")<tool_call|>' not found`로 실패한다.
- **원인:** 모델이 Gemma 고유 형식 대신 프롬프트의 호출 문장 예시를 그대로 출력해 vLLM 해석기가 문장 전체를 이름으로 넘겼다. 깨진 호출이 기록에 쌓이면 계속 따라 한다.
- **해결:** 예시를 설명형으로 바꾸면 정상 호출되는 것을 재현 실험으로 확인했다. 실제 수정은 별도 작업.
  → 이슈: [[issues/describe-schema-tool-call-syntax-in-name]]
- **문제:** 메모리 도구를 켜도 호출되지 않았다.
- **원인:** 기반 프롬프트 캐시와 지시 충돌.
- **해결:** 캐시를 도구 구성별로 나누고 STEP 0과 저장 도구 설명을 넣었다.

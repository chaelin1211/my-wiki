# 2026-10-19 — 회원가입·로그인·계정 관리 고도화 마무리 (`feat/auth-enhancement`)

## 목표

회원가입·로그인 고도화 브랜치를 마무리해 PR로 올린다. 매뉴얼 정리, 남은 보안·사용성 문제 점검, 관리자 계정 관리 화면 다듬기.

## 수행한 작업

1. **매뉴얼 정리** — 사용자·관리자 매뉴얼을 읽는 사람 기준으로 검토(불필요한 내부 설명·과장 표현 제거), 관리자 단락명 "회원 및 권한 관리"와 매뉴얼 사이드바 제목 일치, "DB 연결 생성" 설명을 실제 화면(지원 DB 6종, DSN 칸 없음)에 맞게 다시 씀. 비밀번호 초기화 요청·초기화 두 소단락을 하나로 합침.
2. **72바이트 넘는 비밀번호 500 오류 수정** — 새 비밀번호는 72바이트 이내로 막고, 로그인·현재 비밀번호 확인은 앞 72바이트로 비교. 웹 5곳에서도 입력 단계에서 차단 → [[knowledge/troubleshooting/bcrypt-72-byte-limit]]
3. **PR 생성** — 백엔드 #180, 웹 #102. 이후 커밋을 계속 추가하고, 웹 브랜치에 main(#103 마스킹 태그 정규화, #104 하위 경로 basePath) 병합. 두 PR 모두 충돌 없이 병합 가능 상태로 푸시.
4. **이름·생년월일 선택 항목화** — 회원가입·마이페이지 모두 선택, 둘 다 비우면 확인 창. 이름 없으면 프로필 입력 페이지로 보내던 기능은 제거(`bfa130b` 되돌림).
5. **비밀번호 초기화 요청 재설계** — 이메일 + (이름 또는 생년월일 중 하나)로 본인 확인, 결과와 관계없이 같은 응답. 계정 상태와 무관하게 접수, 일치·불일치·계정 없음 모든 요청을 이력으로 저장(입력값은 저장 안 함) → [[decisions/048-password-reset-identity-and-full-history]]
6. **가입 승인 기록** — `users`에 `signup_type`(approval/auto)·`review_result`·`reviewed_at`·`reviewed_by` 추가, 상태 변경 한 곳(`_UPDATE_STATUS_SQL`)에서 승인·거절 기록. 가입일 = 승인 이력이 있으면 승인 시각, 승인 대기·거절은 없음, 그 밖에는 `created_at` → [[decisions/049-signup-review-record-and-joined-at]]
7. **관리자 계정 관리 탭** — 개요 탭을 "계정 관리"로 바꾸고 한때 가입 신청·초기화 요청 이력 목록(대기 먼저·처리일시순, 처리 칸 버튼 통합)까지 만들었으나, 최종적으로 **가입 방식 토글 + 회원 현황·처리할 요청 카드**(누르면 사용자 목록 필터로 이동)로 되돌림. 조회 API는 백엔드에 남김.
8. **사용자 목록·팝업** — 승인 대기·거절은 가입일 칸에 [거절]·[승인] 버튼, 정보 팝업은 승인/거절 안내만 남기고 비밀번호·시스템 권한·저장 숨김. 표 `table-fixed` + 이름·이메일 말줄임.
9. **회원가입·초기화 요청 화면** — 개인정보 확인 창보다 이메일 중복 확인을 먼저(이메일 사용 가능 여부 API 추가), 없는 날짜 입력 처리, 초기화 요청 화면은 엔터로 제출되지 않게.
10. **테스트 데이터** — test5~test27@mobigen.com 승인 대기 계정 생성, 오래된 테스트 계정 6개 삭제(공용 개발 DB).

## 핵심 결정

- **비밀번호 초기화 본인 확인은 이름 또는 생년월일 중 하나, 응답은 항상 동일, 모든 요청을 이력으로** — "정보가 틀렸다"고 알리면 남의 실명·생일을 대입해 알아낼 수 있어서 응답은 통일. 대신 관리자가 "왜 처리 안 됐나"를 확인할 수 있게 불일치·계정 없음도 기록(입력값 제외).
  → ADR: [[decisions/048-password-reset-identity-and-full-history]]
- **가입 경로·승인 시각을 사용자 표에 기록하고 가입일은 승인 시각 기준** — 승인 방식에서는 승인 순간부터 회원.
  → ADR: [[decisions/049-signup-review-record-and-joined-at]]
- **관리자 화면은 별도 이력 목록 대신 카드 → 사용자 목록 필터** — 두 목록을 만들어 써 보니 사용자 목록과 같은 정보를 두 곳에서 다루게 되어 다시 카드 방식으로. 이력 조회 API는 남겨 둠.

## 배운 것

- 브라우저 `type="date"` 는 없는 날짜(2월 31일, 연도 미입력)면 화면에 숫자가 보여도 값을 빈 문자열로 넘긴다. 일(日) 칸에 99를 치면 포커스 중에는 99로 보이다 벗어날 때 31로 바뀐다 → [[knowledge/troubleshooting/html-date-input-invalid-date-empty-value]]
- PostgreSQL `ORDER BY` 는 출력 별칭을 단독으로는 쓸 수 있지만 `COALESCE(alias, …)` 같은 식 안에서는 못 쓴다. 가짜 DB 단위 테스트로는 못 잡으니 실제 DB로 함수를 불러 봐야 한다 → [[knowledge/troubleshooting/postgres-order-by-alias-in-expression]]
- 공용 개발 DB를 바꿀 때는 트랜잭션 안에서 실행 후 ROLLBACK 으로 먼저 확인하고, 미배포 테이블 변환은 한 번 적용 후 `schema.py` 에는 최종 정의만 남겼다.
- 한 파일에 여러 기능이 섞였을 때 최종본을 백업하고 기능별 중간 단계 파일을 만들어 차례로 커밋한 뒤 최종본과 대조하는 방식이 hunk 단위 분리보다 안전했다.

## 문제 & 해결

- **문제:** 72바이트 넘는 비밀번호(한글 약 25자)로 가입·변경·로그인 시 500
  - **원인:** bcrypt 5.0이 72바이트 초과 입력에 예외를 던짐(예전 버전은 조용히 잘랐음)
  - **해결:** 새 비밀번호 72바이트 제한 + 확인은 앞 72바이트 비교 → [[knowledge/troubleshooting/bcrypt-72-byte-limit]]
- **문제:** 가입일 정렬 추가 후 사용자 목록 API 오류(`column "joined_at" does not exist`)
  - **원인:** `ORDER BY COALESCE(joined_at, …)` 에서 별칭을 식 안에 사용
  - **해결:** 정렬식에 계산식을 그대로 넣음 → [[knowledge/troubleshooting/postgres-order-by-alias-in-expression]]
- 그 밖의 작은 문제는 [[issues/log]]에 한 줄씩 기록.

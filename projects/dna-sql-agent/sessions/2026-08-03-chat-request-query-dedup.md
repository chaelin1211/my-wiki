# 2026-08-03 — 채팅 요청 경로의 중복 DB 조회 정리

## 목표

권한 검증 작업(ADR-029) 과정에서 드러난 중복 조회를 정리한다. 요청 단위로 공유되는
컨텍스트가 없어 각 레이어가 같은 데이터를 각자 조회하고 있었다.

## 수행한 작업

1. **중복 실측** — `chat_sse` 1건당 고정 8회 + SQL 실행 횟수. 스코프 확정 쿼리와
   `get_conversation` 이 같은 대화 행을 두 번 읽고, 프롬프트 빌더와 SQL 가드가 같은
   그룹 권한을 각각 조회하며, 가드는 SQL 실행마다 반복 조회

2. **`get_conversation` 쿼리 통합** — `user_id` 를 함께 읽어 "없음"과 "타인 소유"를
   한 쿼리로 구분. 아무도 읽지 않던 스코프 컬럼 조회 제거

3. **그룹 권한 공유** — 프롬프트 빌더가 최초 조회하고 가드가 재사용. 프롬프트에
   알리는 정책과 실제 차단 기준이 같은 소스가 되는 효과도 있다

4. **시스템 값 전달** — 스코프 확정 쿼리에서 `system_prompt`/`dialect`/`version` 을
   함께 읽어 프롬프트 빌더에 전달. `RequestContext.metadata` 로 나르면 로그에
   프롬프트 본문이 통째로 찍혀 요청 단위 캐시를 썼다

5. **캐시 수명 관리** — `request_scope` 모듈로 생성과 일괄 초기화를 묶음

6. **부수 수정** — 소유자 비교를 UUID 로, `_authorized_scope` → `_scope_from_row` 개명

7. **PR #127, #75 머지** (전날 작업분)

## 핵심 결정

- **결정 1:** 전달 수단으로 `RequestContext.metadata` 대신 `ContextVar` 를 썼다.
  metadata 는 `user.metadata`·`ToolContext.metadata` 로 복사되고 그대로 로그에 찍혀,
  `system_prompt` 본문이 매 요청 로그에 남는다.

- **결정 2:** 캐시 수명은 요청 단위. TTL 캐시로 하면 "권한 뺏었는데 계속 통과"가 생긴다.
  요청마다 새로 조회하되 한 요청 안의 중복만 없앤다.

- **결정 3:** `request_scoped_cache()` 로 만든 것만 초기화 대상이 되게 했다. 캐시가
  늘어날 때 WebSocket 초기화를 빠뜨리는 것을 구조적으로 막는다.

## 배운 것

- **ContextVar 의 수명은 "요청"이 아니라 "태스크"다.** HTTP 는 요청마다 태스크가 생겨
  결과적으로 요청 단위가 되지만, WebSocket 은 연결 하나가 while 루프로 여러 메시지를
  처리해 컨텍스트가 이어진다. "요청 단위"라는 전제가 프로토콜에 따라 깨진다.

- **전파 방향은 단방향이다.** 태스크 생성 시점의 값은 복사되어 자식에게 보이지만,
  자식이 `set()` 한 값은 부모로 돌아오지 않는다. 그래서 엔드포인트(1단계)에서 채운
  캐시가 제너레이터(2단계)에서 보이는지 확인이 필요했다.

- **프레임워크 소스를 보면 알 수 있는 걸 "돌려봐야 안다"고 미뤘다.** Starlette
  `StreamingResponse.__call__` 을 확인하니 두 경로(`await` / `task_group.start_soon`)
  모두 전파가 보장됐다. 사용자 지적으로 확인했다.

- **결과가 같으면 캐시 적중 여부를 알 수 없다.** 캐시가 빗나가도 폴백 쿼리가 같은 답을
  주므로 프롬프트 내용만 봐서는 절감 효과를 검증할 수 없다. 임시 로그로 확인했다.

## 문제 & 해결

- **문제:** WebSocket 경로에서 캐시가 연결 내내 유지돼 권한 회수가 반영되지 않음
- **원인:** `while True` 루프 하나가 연결 전체를 처리 = 한 태스크. ContextVar 는 태스크
  단위라 메시지가 바뀌어도 컨텍스트가 그대로다
- **해결:** 루프 시작 시 `reset_request_caches()`. 현재 프론트는 WS 를 쓰지 않아 실제
  노출 경로는 아니지만 엔드포인트가 살아 있어 미리 막았다
  → 패턴: [[knowledge/patterns/request-scoped-cache-with-contextvars]]

- **문제:** 소유권 비교를 SQL `WHERE` 에서 파이썬 문자열 비교로 옮기며 정당한 소유자가
  거부될 수 있는 상태가 됨
- **원인:** Postgres 가 하던 UUID 정규화가 사라짐. JWT `sub` 표기가 다르면(대문자 등) 불일치
- **해결:** `_same_user()` 로 UUID 비교. 대문자·urn 형식 등 5케이스 테스트

# ADR-041: 슬래시 커맨드 정의는 DB에, 실행 로직만 코드에

## 맥락

채팅 입력창에서 `/`를 치면 쓸 수 있는 커맨드 목록을 보여 주려 했다. 기존 커맨드(`/help`, `/status`, `/memories`, `/delete`)는 `DefaultWorkflowHandler`의 조건문에 이름·설명·권한이 흩어져 있어 목록을 만들 방법이 없었고, `help`·`status` 같은 `/` 없는 별칭이 일반 질문을 가로챘다. 또 관리자가 안내문이나 LLM 스킬을 코드 수정 없이 추가하고, 이후 사용자 생성 커맨드로 넓힐 여지가 필요했다.

## 선택지

### 옵션 A: 코드 레지스트리
- **장점:** 실행 로직과 정의가 한곳에 있고 타입 검사가 된다.
- **단점:** 커맨드를 추가하려면 코드 수정과 배포가 필요하다.
- **비용/노력:** 작음.

### 옵션 B: 설정 디렉터리의 `.md` 파일 (`skills/<name>/SKILL.md`)
- **장점:** 편집기와 git으로 관리하기 좋고 참고 파일을 함께 둘 수 있다. 기존 `config/` 바인드 마운트 구조와 같다.
- **단점:** 등록 시점에 형식을 강제할 수 없고, 서버가 여러 대면 파일을 따로 맞춰야 하며, 사용자 생성 커맨드로 넓히기 어렵다.
- **비용/노력:** 중간.

### 옵션 C: DB 테이블 (`slash_commands`)
- **장점:** 테이블 제약으로 형식 강제, 다중 서버에서 자동 일치, 관리 API·화면을 붙이기 쉽다.
- **단점:** 실행 로직(builtin)은 DB에 둘 수 없어 코드 매핑이 남는다.
- **비용/노력:** 중간.

## 결정

**옵션 C를 선택한다.** 커맨드 이름·설명·사용 예시·공개 범위·실행 방식·본문·사용 여부는 DB에 두고, 코드에는 `action_key` → 실행 함수 매핑(builtin)만 둔다.

- 실행 방식: `builtin`(서버 기능), `text`(고정 안내문), `skill`(지시문 + 사용자 입력을 LLM에 전달).
- 공개 범위: `public`, `admin`. 그룹 관리자 범위는 필요한 커맨드가 확인될 때까지 두지 않는다.
- 이름은 영문 소문자로 시작하는 `[a-z][a-z0-9_-]{0,31}`, 별칭 없음. 메시지 첫 글자가 `/`일 때만 커맨드로 해석한다.
- 등록은 관리자만(관리자 API), 관리 화면은 보류.

## 근거

목록 제공이 목적이므로 정식 이름 하나면 충분하고, 이름은 대화 이력 메타데이터와 감사 로그가 커맨드를 가리키는 키라 바꿀 수 없게 했다. 파일 방식은 형식 오류를 불러올 때에야 알 수 있고 서버 간 동기화가 필요해, 납품 환경에서 관리 부담이 크다.

## 결과

- builtin 커맨드는 삭제·이름·공개 범위·실행 방식 변경을 API에서 막고, `/help`는 끌 수 없다. 코드에 실행 함수가 없는 builtin은 목록에서도 뺀다.
- 권한 밖 커맨드도 "알 수 없는 커맨드"로 응답해 관리자 커맨드 존재를 드러내지 않는다. 실제 사유는 감사 로그에만 남긴다.
- 캐시를 두지 않고 `/` 메시지마다 DB를 조회한다. 등록·수정이 재시작 없이 반영된다.
- 영향: `src/dna/commands/`, `DnaWorkflowHandler`, `schema.py`, 웹 입력창 목록.

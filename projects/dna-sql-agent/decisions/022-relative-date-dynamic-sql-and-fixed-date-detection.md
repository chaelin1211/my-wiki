# ADR-022: 상대 날짜는 DB 동적 함수로 생성 + 대시보드에 고정 날짜 감지·경고 병행

## 맥락

북마크·대시보드 위젯은 생성 시점의 SQL(`query_sql`)을 그대로 저장했다가, "갱신" 시
동일한 SQL을 재실행한다. 그런데 시스템 프롬프트가 "사용자가 '오늘/최근 3일/이번 주'
같은 날짜 질의를 하면 기준 일시를 바탕으로 계산해서 SQL을 작성하라"고 지시하고 있어,
LLM이 상대 날짜를 **그 순간 계산된 리터럴**(`WHERE date >= '2026-07-01'`)로 SQL에
박아 넣는다. 이렇게 저장된 쿼리는 며칠 뒤 "갱신"해도 그 과거 날짜 그대로 고정되어,
"최근 7일" 위젯이 실제로는 절대 굴러가지 않는 문제가 있다.

(참고: 같은 시점에 LIMIT도 저장 직전에 SQL에 주입되는 방식이라, 두 문제가 유사한
모양을 하고 있었다 — [[issues/bookmark-query-sql-limit-not-injected]])

## 선택지

### 옵션 A: 프롬프트 지시만 변경
- **장점:** 구현이 가장 단순, 다른 컴포넌트 변경 불필요
- **단점:** LLM이 지시를 안 따를 가능성이 항상 있음(모델/버전에 따라 편차) — 보장이 없음
- **비용/노력:** 매우 낮음

### 옵션 B: 프롬프트 지시 변경 + 대시보드에 고정 날짜 감지·경고 UI 병행 (선택)
- **장점:** 프롬프트가 실패해도(리터럴이 새 나가도) 사용자가 눈으로 알아챌 수 있음. 감지 로직이 "날짜 리터럴이 있는지"만 보고 "오래됐는지"는 안 봐서 매우 단순 — 오탐 없이 안내용으로만 씀
- **단점:** 근본적으로 SQL을 고치는 건 아니라서, 리터럴이 낀 쿼리 자체는 여전히 존재. 경고만 뜰 뿐 자동 수정은 안 됨
- **비용/노력:** 중간 — 백엔드(정규식 탐지, API 필드 추가) + 프론트(아이콘/툴팁) 양쪽 필요

### 옵션 C: 저장 시점에 SQL을 파싱해서 리터럴 날짜를 동적 함수로 자동 치환
- **장점:** 근본 해결처럼 보임
- **단점:** SQL 파싱/리라이팅은 방언별로 다르고(Oracle/Postgres/MySQL), "이 날짜가 상대 표현에서 온 건지 사용자가 명시한 절대 날짜인지" SQL 텍스트만으론 구분 불가 — 오탐 시 사용자가 의도한 고정 기간까지 잘못 바꿔버릴 위험. 유지보수 비용도 큼
- **비용/노력:** 높음, 리스크 큼

## 결정

**옵션 B를 선택한다.**

## 근거

옵션 A는 사용자에게 "혹시 모를 상황"에 대한 가시성을 전혀 주지 못한다. 옵션 C는
SQL 리라이팅의 오탐 리스크(사용자가 의도적으로 고정한 날짜까지 건드릴 수 있음)가
감지·경고보다 훨씬 크고, 이 프로젝트에서 SQL을 사후 가공하는 다른 사례(LIMIT 주입)도
"저장 직전 주입"이지 "생성된 SQL을 재해석/재작성"은 아니었다는 점에서 일관성이 없다.
B는 프롬프트로 최대한 예방하되, 실패 케이스에 대해 사용자 판단에 맡기는 안전망을
두는 절충안이다.

감지 로직을 "오래됐는지"까지 보지 않고 "날짜 리터럴 존재 여부"만 보기로 한 것도
같은 맥락의 결정이다 — "오래됐는지"는 결국 "이 리터럴이 상대 표현에서 온 건지"를
추정하려는 대리 지표일 뿐이라 여전히 오탐/누락이 생기고, 로직만 복잡해진다. 존재
여부만 보면 판단 기준이 항상 참(그 사실 자체는 거짓일 수 없음)이라 오탐이 없고,
사용자가 직접 판단하면 된다.

## 결과

- 시스템 프롬프트: 상대 날짜(오늘/최근 N일/이번 주 등)는 `CURRENT_DATE`/`INTERVAL` 등
  DB 방언의 동적 함수로 쓰도록 지시. 사용자가 명시한 절대 기간은 기존대로 리터럴 유지.
  (`src/dna/prompt_builders/dna_system_prompt_builder.py`)
- 대시보드 위젯 API(`WidgetResponse`)에 `has_fixed_date_literal: bool` 추가 —
  `query_sql`에 `'YYYY-MM-DD'` 형태 리터럴이 있으면 true. (`src/dna/dashboards/routes.py`)
- 프론트 대시보드 위젯 푸터/확대 팝업에 경고 아이콘(⚠️ TriangleAlert) + 툴팁
  ("조회 조건에 날짜가 고정되어 있는 것으로 의심됩니다...") 표시.
- 향후 재검토 시점: LLM이 이 지시를 얼마나 잘 따르는지 실사용 피드백이 쌓이면,
  경고가 너무 자주 뜨는지(프롬프트 실효성 낮음) 판단해서 프롬프트 문구를 더
  강하게 하거나 few-shot 예시를 추가하는 걸 고려.
- 관련: [[issues/bookmark-query-sql-limit-not-injected]] (같은 "저장 시점에
  SQL에 값을 박아 넣는" 패턴이 다른 문제로 이어진 선례)

# ADR-048: 비밀번호 초기화 요청 — 이름 또는 생년월일로 본인 확인, 응답은 항상 동일, 모든 요청을 이력으로

## 맥락

로그인 없이 쓰는 비밀번호 초기화 요청은 처음에 "이메일 + 이름(필수)"을 받아, 일치하는 요청만 관리자에게 접수하고 응답은 결과와 관계없이 같게 했다. 이후 이름을 선택 항목으로 바꾸면서 본인 확인 수단을 다시 정해야 했고, 운영 중 "요청했는데 왜 안 해 줘"에 관리자가 답할 근거가 없다는 문제가 나왔다.

검토한 위험:

- "계정이 없거나 정보가 잘못됐다"처럼 실패를 알려 주면, 회원가입이 이미 이메일 존재 여부를 알려 주므로 **남의 이메일에 이름·생일을 바꿔 넣어 실명·생일을 알아낼 수 있다.** 실패 사유를 뭉뚱그려도 성공/실패가 구분되는 한 같다.
- 생년월일은 이름보다 맞히기 쉽다(나이를 알면 365가지).
- 로그인 없이 호출되므로 무엇을 저장하든 반복 호출로 쌓일 수 있다.

## 선택지

### 옵션 A: 실패 사유를 알려 준다 (계정 없음/정보 불일치)
- **장점:** 사용자가 오타를 바로 안다.
- **단점:** 실명·생일 대입 노출. 요청 횟수 제한이 필수.

### 옵션 B: 응답은 항상 같고, 일치한 요청만 저장
- **장점:** 노출 없음, 저장량 작음.
- **단점:** 관리자가 불일치 요청을 전혀 볼 수 없어 문의에 답하지 못한다.

### 옵션 C: 응답은 항상 같고, 모든 요청을 이력으로 저장 (입력값은 제외)
- **장점:** 노출 없음. 관리자가 "생년월일 불일치로 들어왔다", "가입 안 된 이메일이다"까지 확인 가능.
- **단점:** 로그인 없이 호출되는 주소라 "계정 없음" 이력이 계속 쌓일 수 있다(보관 기간·횟수 제한 미정).

## 결정

**옵션 C를 선택한다.**

- 본인 확인은 이메일 + **이름 또는 생년월일 중 정확히 하나**(둘 다·둘 다 없음은 422).
- 응답 문구는 결과와 관계없이 "입력한 정보가 가입 정보와 일치하면 관리자에게 요청이 전달됩니다".
- `password_reset_requests` 에 요청마다 한 줄: `email`, `user_id`(계정 없으면 NULL), `method`(name/birth_date), `result`(accepted/mismatch/no_account), `status`(접수된 건만: open/reset/dismissed/self_login). **입력한 이름·생년월일 값은 저장하지 않는다.**
- 계정 상태(비활성·승인 대기·거절)와 관계없이 일치하면 접수한다. 관리자 팝업에 상태를 함께 안내.
- 같은 사용자의 대기 요청이 여러 건이면 초기화·무시 한 번으로 모두 닫는다(사용자 단위 처리).

## 근거

- 노출을 막는 것은 "응답 통일"이고, 운영 문의 대응은 "서버 기록"으로 해결된다. 두 요구가 충돌하지 않는다.
- 입력값까지 저장하면 대입 시도의 개인정보가 쌓이므로, 사유(결과·방법)만 남겨도 문의 대응에 충분하다.

## 결과

- 관리자 화면에서 이력 목록은 한 번 만들었다가 사용자 목록 필터 방식으로 되돌렸다. 조회 API(`GET /admin/password-reset-requests`, 일괄 무시)는 남겨 두었고 기록은 계속된다.
- 남은 과제: 요청 횟수 제한, 이력 보관 기간(90일안은 정책 미정이라 보류).
- 생년월일로 접수된 요청은 관리자가 한 번 더 본인 확인하도록 매뉴얼에 안내.

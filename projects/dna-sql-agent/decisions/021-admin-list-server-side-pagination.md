# ADR-021: 관리자 목록(연결/시스템/사용자/그룹)을 서버사이드 페이징으로 전환

## 맥락

관리자 화면의 4개 목록(DB 연결, DB 시스템, 사용자, 그룹)이 전부 "전체 목록을 한 번에 불러와 클라이언트에서 렌더링"하는 방식이었다. 목록이 커지면 응답이 느려지고, 페이지 이동도 실제로는 클라이언트 배열 슬라이싱에 불과했다.

다만 사용자/그룹 목록은 단순 나열 화면 외에도:
- 그룹 필터 드롭다운(사용자 목록에서 그룹으로 필터링)
- 그룹별 소속 사용자 수 집계
- 그룹 멤버 관리 다이얼로그(전체 사용자 중 검색해서 추가/제거)

처럼 **전체 목록이 필요한 부가 기능**이 이미 존재했다. 이걸 무시하고 목록 API를 페이징으로만 바꾸면 이 기능들이 깨진다.

## 선택지

### 옵션 A: 4개 목록 API 모두 페이징으로 통일, 부가 기능은 각자 별도 API 호출로 대체
- **장점:** 목록 API가 단일 책임(페이지 단위 조회)만 가짐, 일관성
- **단점:** 부가 기능마다 별도 API가 필요해 엔드포인트 수 증가
- **비용/노력:** 중간

### 옵션 B: 페이징 API를 안 만들고 프론트에서 클라이언트 사이드 페이징 유지, 렌더링 성능만 개선
- **장점:** 백엔드 변경 없음
- **단점:** 데이터가 많아지면 근본적으로 느림, 애초에 이번 작업의 동기를 해결 못 함
- **비용/노력:** 낮음이지만 문제 해결 안 됨

## 결정

**옵션 A를 채택한다.** 단, 무페이징 전체 조회 API는 삭제하지 않고 그대로 남겨(또는 신설해) 부가 기능 전용으로 계속 사용한다.

- 연결/시스템: 기존 무페이징 `/connections`, `/systems`는 다른 화면(relation-viewer, 시스템 선택 드롭다운 등)에서 이미 쓰이고 있어 그대로 두고, `/connections/paged`, `/systems/paged`를 신설
- 사용자: `/admin/users`를 페이징(`page`/`page_size`/`search`)으로 전환하고, 그룹 멤버 관리처럼 전체 목록이 필요한 화면 전용으로 `/admin/users/roster`(무페이징) 신설
- 그룹: 기존 무페이징 `/admin/groups`는 필터 드롭다운 등에 그대로 두고, 그룹별 사용자 수까지 포함한 `/admin/groups/paged` 신설

프론트에는 공통 `DataPagination` 컴포넌트(중앙 정렬, 화살표, 생략된 페이지 번호)를 만들어 4개 목록이 동일한 UI를 쓰도록 통일했다.

## 근거

- 페이징이 필요한 곳(단순 목록 나열)과 전체 목록이 필요한 곳(필터/집계/멤버관리)의 요구사항이 근본적으로 다르다 — 하나의 API로 두 요구를 억지로 만족시키려 하면 응답에 항상 `total`/`items` 래퍼가 붙어 기존 호출부를 전부 고쳐야 하거나, 페이징 응답 안에 전체 목록도 우겨넣는 기형적인 API가 된다.
- 기존에 이미 같은 문제를 겪고 정석적으로 풀어놓은 사례(`GET /admin/users/systems` — `PaginatedUserWithSystemsResponse`, LIMIT/OFFSET + COUNT(*) 패턴)가 코드베이스에 있어서 그 패턴을 그대로 재사용했다.

## 결과

- 엔드포인트 수는 늘었지만(각 리소스당 페이징/무페이징 2개), 각 API의 책임이 명확해져 유지보수 부담은 오히려 줄었다.
- 프론트 훅(`useDbConnections`, `useDbSystems`, `useUsers`+`useUsersRoster`, `useGroups`+`useGroupsPaged`)도 역할별로 분리되어, 어느 화면이 어떤 데이터를 쓰는지 이름만 보고 알 수 있다.
- 향후 페이지 크기가 커지거나(현재 20) 목록이 매우 커지는 리소스가 생기면 같은 패턴을 그대로 적용하면 된다.

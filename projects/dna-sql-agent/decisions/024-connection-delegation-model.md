# ADR-024: 그룹↔커넥션 위임 모델 (그룹↔시스템 매핑 자동 파생화)

## 맥락

[[decisions/023-group-admin-role-and-permission-model|ADR-023]]에서 확정한
`group_system_mappings`(그룹↔시스템 매핑)는 시스템 관리자가 수동으로 편집하는
단일 정책 레이어였다. 커넥션(DB 서버 접속 정보) 관리 권한은 이 매핑에서
파생되는 것으로 취급했는데, "매핑된 시스템이 하나라도 있으면 커넥션도 편집
가능"이라는 정책(v0.4, `docs/group-admin-design.md`)이 실제로는 "생성자만
편집" 같은 더 세밀한 통제가 필요하다는 요구와 충돌해 2026-07-20 하루 사이에
설계→구현→보류를 반복했다 (백엔드 `_require_connection_visible` 등 스코프
체크 코드를 만들었다가 "임시로 시스템 관리자와 동일하게 전체 개방"으로
되돌린 상태로 남아 있었음).

이 ADR은 그 재조정 끝에 확정된 새 모델(정책 문서 v0.5)의 구조적 결정만
요약한다. 전체 정책은 `docs/group-admin-design.md` v0.5 §3, §4.1 참고.

## 선택지

### 옵션 A: 커넥션 접근을 계속 시스템 매핑에서 파생시킨다 (v0.3/v0.4 연장)
- **장점:** 이미 있는 `group_system_mappings` 하나로 커넥션·시스템 접근을 모두 설명
- **단점:** "커넥션 하나에 시스템이 여러 개, 그룹마다 접근 가능한 시스템이 다름"
  케이스에서 커넥션 자체의 관리 권한(등록·수정·삭제)을 어떤 그룹 기준으로 판단할지
  일관된 규칙을 못 만듦 — v0.3(단독 소유만 편집)과 v0.4(공유 무관 전체 편집) 둘 다
  실제 요구사항과 어긋나 하루 만에 뒤집힘

### 옵션 B: 커넥션 단위로 별도 위임 레이어를 추가한다
- **장점:** 커넥션 CRUD는 시스템 관리자 전용으로 단순화하고, 그룹에는 "이 커넥션
  위에서 시스템을 관리해도 된다"는 권한만 명시적으로 위임(N:M). 시스템 단위 접근은
  이 위임 + 생성 주체(그룹 관리자 vs 시스템 관리자) 규칙만으로 100% 자동 결정 —
  시스템 관리자가 개별 시스템을 그룹에 손으로 매핑하는 화면 자체가 불필요해짐
- **단점:** 새 매핑 테이블(`group_connection_mappings`)과 자동 매핑/캐스케이드
  로직(시스템 생성 시, 위임 해제 시)이 추가로 필요
- **비용/노력:** 스키마 1개 + CRUD API + 자동 매핑 트리거 로직 + 그룹 관리자용
  연결 관리 화면을 조회 전용으로 축소

## 결정

**옵션 B를 선택한다.**

- `group_connection_mappings(group_id, connection_id)` 신설 (N:M). 시스템
  관리자만 CRUD, 위임해도 시스템 관리자 본인 권한은 유지.
- `group_system_mappings`는 더 이상 시스템 관리자가 수동으로 만드는 레코드가
  아니라, 아래 규칙으로 **자동 생성/삭제**되는 파생 상태로 격하:
  - 그룹 관리자가 시스템을 생성 → 생성한 그룹에만 매핑 (다른 그룹은 위임을
    받았어도 조회조차 안 됨 — 그룹 관리자 생성 시스템은 항상 배타적 소유)
  - 시스템 관리자가 시스템을 생성 → 그 커넥션을 위임받은 모든 그룹에 매핑
    (여러 그룹이 동시에 관리 가능한 "공유 시스템"이 될 수 있음)
  - 커넥션이 그룹에 새로 위임되면, 그 커넥션 위 "시스템 관리자가 생성한" 기존
    시스템들도 소급 매핑
  - 위임이 해제되면 관련 매핑 전부 해제. 그중 해제 대상 그룹이 직접 만든
    시스템은 상태를 미사용(inactive)으로 전환, 시스템 관리자 생성 공유
    시스템은 매핑만 해제하고 상태 유지. 매핑이 끊긴 시스템에 대한 그 그룹
    사용자들의 `user_system_permissions`도 함께 자동 회수 (ADR-023의 매핑
    해제 시 권한 자동 회수 원칙을 위임 해제 경로까지 연장 적용)
- 그룹 관리자용 연결 관리 화면은 위임받은 커넥션 **조회 전용**으로 축소 —
  등록·수정·삭제 UI 제거.

## 근거

- "시스템 단위로 그룹 접근을 세밀하게 고른다"는 유연성보다, "커넥션 단위로
  위임하면 그 안은 자동으로 정리된다"는 단순함과 예측 가능성을 우선했다.
  실제로 v0.3/v0.4가 하루 만에 뒤집힌 이유가 세밀한 규칙(단독 소유/공유 판정)을
  임기응변으로 조정하다 생긴 것이었으므로, 규칙을 줄이는 방향이 더 안정적이라고
  판단.
- 시스템 생성 시 그룹 매핑을 수동으로 거는 별도 화면이 있으면 "위임했는데
  실제로는 그룹이 아무 시스템도 못 봄" 같은 2단계 설정 누락이 생길 여지가
  있다. 자동 파생으로 만들면 위임 = 즉시 사용 가능이 보장된다.
- 위임 해제 시 캐스케이드(매핑 해제 → 미사용 전환/유지 분기 → 사용자 권한
  회수)를 명문화해둔 덕분에, 나중에 구현할 때 "권한이 유령처럼 남는" 상태를
  방지하는 규칙을 다시 설계할 필요가 없다.

## 결과

- **아직 구현 전 — 정책만 확정.** 신규 스키마(`group_connection_mappings`),
  기존 "임시 전체 개방"이던 그룹 관리자용 커넥션 CRUD 엔드포인트 제거, 자동
  매핑/캐스케이드 로직, 프론트엔드 연결 관리 화면 조회 전용화가 모두 남은
  작업이다 ([[projects/dna-sql-agent/status|status.md]] 2026-07-20 이월 항목
  참고).
- 그룹 관리자 기능이 아직 정식 릴리즈되지 않은 상태라 기존 데이터에 대한
  소급 마이그레이션은 하지 않기로 했다 — 정책 적용 이후 시스템 관리자가
  필요한 위임을 새로 설정한다.
- ADR-023의 "이중 레이어" 설명(그룹↔시스템 매핑 vs 사용자↔시스템 권한)은
  이제 그 위에 그룹↔커넥션 위임이 추가된 **삼중 레이어**로 확장됐다. ADR-023
  자체는 관계 테이블 vs 역할 방식 선택 등 여전히 유효한 내용이 더 많아 폐기하지
  않고, 커넥션 관련 서술만 이 ADR로 대체하는 것으로 처리한다.
- 향후 재검토 시점: 만약 "커넥션 위임 없이 특정 시스템 하나만 그룹에 공유"하는
  요구가 실제로 생기면, 이번에 일부러 빼기로 한 시스템 단위 수동 매핑을 다시
  넣어야 할 수 있다 (`docs/group-admin-design.md` §5 "제외 항목" 참고).

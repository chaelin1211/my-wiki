# ADR-052: 도구 접근 제어는 실행만, 그룹별 화면 정보 표시는 표시만 담당 (도구별 표시 추가)

## 맥락

관리자 화면 인프라 메뉴의 두 카드가 서로의 역할을 침범하고, 항목 이름이 실제 동작과 맞지 않는다. 코드와 로그로 확인한 현재 동작은 다음과 같다.

**도구 접근 제어 카드가 표시까지 정한다.** 그룹 체크는 LLM 노출(`get_schemas`)과 실행(`registry.execute`)을 정하는데, 결과 화면을 보여줄지도 같은 기준(`agent.py`의 `can_see_tool_output = has_tool_access(...)`)으로 정한다. 실행 권한이 없으면 이미 결과가 없으므로 이 판정은 중복이다.

**그룹별 화면 정보 표시 항목이 겹치거나 실제와 다르다.**

| 항목 (키) | 실제로 켜고 끄는 것 | 문제 |
|---|---|---|
| 도구명 (`tool_names`) | 진행 목록의 "호출 도구 : ○○" 줄. | 도구 파라미터 카드 제목에도 도구 이름이 들어가 있어서, 도구명을 꺼도 이름이 보인다. |
| 도구 파라미터 (`tool_arguments`) | ⚙ 도구 카드 전체(이름·상태·인자·성공/실패 문구). | 하나의 항목이 카드 전체를 켜고 끈다. 실패 문구 "도구 실패 : 에러내용"이 들어 있어서 도구 에러를 꺼도 에러가 보인다. |
| 도구 에러 (`tool_error`) | 실패한 도구의 결과 화면. | 위와 같이 에러 내용이 다른 항목으로 샌다. |
| 호출 메시지 (`tool_invocation_message_in_chat`) | 도구 호출 직전 AI 문장을 본문("도구 호출 과정" 블록)에 남길지와 답변 스트리밍 여부(`_can_stream_text`). | 특정 도구와 관계가 없다. 지금 모델(gemma-4, vLLM)은 도구를 호출할 때 문장을 쓰지 않아서(`content=''`) 사실상 스트리밍 설정으로만 동작한다. 대화를 다시 열면 권한과 상관없이 문장이 보인다(`build-steps.ts`). |
| 메모리 결과 (`memory_detailed_results`) | "도구 사용 사례 검색" 도구 하나의 결과를 카드로 보일지, 상태바 한 줄로 바꿀지. | 도구 하나 전용인데 공통 항목에 있다. 분기가 공통 판정이 아니라 도구 코드(`agent_memory.py`) 안에 있다. 상태바 한 줄은 영어 고정 문구이고 대화 기록에 남지 않는다. |

**판정 기준.** 각 항목은 표의 열(권한 그룹)에서 ✓를 켠 그룹에 사용자 그룹이 들어 있으면 허용한다. 사용자는 그룹이 하나이고 토큰의 `group` 값으로 판정한다. 체크가 하나도 없으면 전원 거부다.

**메모리 도구가 동작하지 않았다.** 도구 사용 사례 검색(`SearchSavedCorrectToolUsesTool`)과 질문·도구 인자 저장(`SaveQuestionToolArgsTool`)을 켜도 호출되지 않았다. 원인은 두 가지다.

- 기반 프롬프트(dadap `DefaultSystemPromptBuilder`)를 처음 한 번만 만들고 고정해서, 도구를 나중에 켜도 프롬프트 속 도구 목록과 메모리 안내가 바뀌지 않았다. 2026-10-20 로그에서 64건이 메모리 도구 없는 옛 목록이었다.
- `vector_search`를 반드시 먼저 부르라는 지시와 "search_saved_correct_tool_uses는 구조를 알려주지 않는다"는 문장(커밋 `f41fc995`, 2026-09-08)이 검색 도구를 밀어냈다. 그 뒤로 실제 호출이 없었다.

이 기능은 유지해야 한다.

## 선택지

### 옵션 A: 현재 구조 유지, 항목 이름만 정리
- **장점:** 작업량이 적다.
- **단점:** 표시가 실행 권한에 묶인 문제, 항목 간 정보 누출, 도구별 설정 불가가 그대로 남는다.
- **비용/노력:** 프론트 문구 수정만.

### 옵션 B: 실행과 표시를 분리하고, 공통 기본값 + 도구별 예외로 표시를 설정
- **장점:** 카드마다 역할이 하나다. 정보 하나는 항목 하나에서만 켜고 끈다. 도구마다 다르게 보여줄 수 있다. 메인 화면은 지금 모양을 유지하고 도구별 설정은 팝업으로 분리해 화면이 복잡해지지 않는다.
- **단점:** 표시 판정을 한 곳으로 모으는 백엔드 정리와 새 테이블이 필요하다. 기존 권한을 옮겨야 한다.
- **비용/노력:** 백엔드 판정 헬퍼, DB 테이블 1개, 설정 화면 수정.

### 옵션 C: 도구 × 항목 × 그룹을 한 표에 전부 펼침
- **장점:** 모든 설정이 한눈에 보인다.
- **단점:** 도구 9개 × 항목 5개면 45행이고, 대부분의 칸이 기본값과 같다.
- **비용/노력:** 옵션 B와 비슷하고 화면이 복잡하다.

## 결정

**옵션 B를 선택한다.** 아래 1~6은 처음 제안한 내용이고, 구현하면서 바뀐 점은 바로 아래 "최종 구현"이 정본이다.

### 최종 구현 (2026-10-23, PR 백엔드 #186 · 웹 #107)

- **도구 접근 제어는 실행만.** 그룹 권한은 LLM 노출(`get_schemas`)과 실행(`registry.execute`)만 정하고, 결과 표시 판정에서 `has_tool_access`를 뺐다.
- **화면 표시 항목은 5개.** 도구 실행 표시 4개(진행 단계 `tool_names`, 실행 상세 `tool_arguments`, 결과 화면 `tool_result`, 에러 상세 `tool_error`)와 AI 응답 표시 1개(답변 스트리밍 `tool_invocation_message_in_chat`)다. 실행 카드와 실행 인자는 나누지 않았다. 인자를 뺀 카드는 진행 단계와 같은 정보에 성공/실패만 더해 따로 켜고 끌 가치가 없었다. 에러 상세를 끄면 실행 카드에도 "도구 실패"만 남는다.
- **판정 통합.** `agent.py`의 표시 판정은 `_can_show(feature, user, …, tool_name)` 하나로 모았고, 감사 로그도 그 안에서 남긴다. 판정은 `UiFeatures.can_user_see`로, 도구별 예외가 있으면 그 값, 없으면 그룹 허용을 따른다.
- **질문 확인 카드는 항상 표시.** `clarify_request` 결과는 결과 화면 권한과 도구별 예외를 보지 않는다. DB가 아니라 코드 상수다(백엔드 `agent_service.py`의 `UiFeatures(always_visible_result_tools=["clarify_request"])`, 프론트 `tool-display-overrides.tsx`의 잠금용 `['ClarifyRequestTool']`). 대상이 늘면 두 곳을 같이 고쳐야 한다.
- **메모리 결과 항목은 없앴다.** 사례 검색 도구는 항상 상세 카드를 만들고, 다른 도구처럼 결과 화면이 정한다. 옛 키 `memory_detailed_results`는 기동 시 운영 설정과 DB 권한에서 지운다(`RETIRED_UI_FEATURES`). 도구별 예외로 옮기지 않고 지웠다. 차이가 나는 그룹이 test3 하나였고, 필요하면 팝업에서 다시 숨기면 된다.
- **사례 저장 결과는 카드.** 상태바 "Saved to memory" 대신 질문·도구·인자가 담긴 "Memory Saved" 카드를 낸다.
- **도구별 세부 조정.** `tool_display_overrides` 테이블(행 없음 = 기본 따름)과 `GET/PUT /api/v1/group-permissions/tool-display/overrides`를 추가했다. 저장 후 적용 대기(`tool_display_overrides` 표식)를 거쳐 `reload_permissions()`가 클래스명을 호출 이름으로 바꿔 넣는다. 버튼은 표 아래가 아니라 "도구 실행 표시" 제목 줄 오른쪽(표 위)에 두었다. 저장 안 한 변경은 버튼·드롭다운·칸에 점으로, 예외가 있는 도구는 드롭다운에 primary 색 "예외" 글자로 표시한다. 칸은 처음 제안한 3단계(기본 따름 / 표시 / 숨김) 대신 **기본값을 따름 ↔ 기본값과 반대** 두 상태 토글로 바꿨다(2026-10-26). 기본값과 같은 값을 따로 지정하는 상태는 화면에서 구분되지 않아 헷갈리기만 했다.
- **신규 그룹 기본.** 화면 정보 표시 두 표에도 도구 카드처럼 "신규 그룹 기본"(`default_access`) 열을 두었다. 기본값은 진행 단계·결과 화면이 켜짐. 도구별 세부 조정에는 신규 그룹 기본을 두지 않았다(새 그룹은 기본값을 따르고, 예외는 그룹을 만든 뒤 지정).
- **권한 마이그레이션.** 새 항목(결과 화면)은 업데이트 후 첫 기동 때 전 그룹에 한 번 부여한다. 도구와 같은 `pending_permission_seed` 표식 방식이라, 관리자가 나중에 전부 해제해도 재시작으로 되살아나지 않는다.
- **대화 기록.** `GET /api/v1/chat/{id}`가 답변 스트리밍 권한 없는 사용자에게는 도구 호출 assistant 메시지의 문장을 비워 보낸다.
- **그룹 순서 통일.** 권한 표가 쓰는 `GET /admin/groups`를 그룹 탭과 같은 순서(admin → 기본 그룹 → 이름, `GROUP_LIST_ORDER`)로 맞췄다.
- **화면.** 인프라 탭 카드 순서를 감사 로그 → 도구 접근 제어 → 그룹별 화면 정보 표시 → 쿼리 비용 예측기로 바꿨다. 항목 설명은 ⓘ 툴팁이다.

### 1. 도구 접근 제어 카드: 실행 권한만

- 사용 여부는 시스템 전체 등록(`tool_access.json`의 `enabled`), 그룹 체크는 그 그룹 사용자가 대화할 때 AI가 도구를 호출할 수 있는지만 뜻한다.
- 설명 문구는 "그룹별로 AI가 호출할 수 있는 도구를 설정합니다."로 바꾼다.
- 결과 표시 판정에서 `has_tool_access`를 뺀다.

### 2. 그룹별 화면 정보 표시 카드: 표시만, 항목 정리

> **구현 중 변경 (2026-10-22~23).** 실행 카드와 실행 인자는 나누지 않고 "실행 상세"(`tool_arguments`) 하나로 둔다. 인자를 뺀 카드는 진행 단계와 같은 도구 이름에 성공/실패만 더해 따로 켜고 끌 가치가 없었다. 메모리 결과(`memory_detailed_results`)는 PR 2를 기다리지 않고 공통 항목에서 없앴다. 사례 검색 도구는 항상 상세 카드를 만들고, 보일지는 다른 도구처럼 결과 화면(`tool_result`)이 정한다. 기존 설정 파일과 DB의 이 키는 기동할 때 지운다. 그래서 최종 항목은 도구 실행 표시 4개(진행 단계, 실행 상세, 결과 화면, 에러 상세)와 AI 응답 표시 1개(답변 스트리밍)다. 아래 표는 처음 제안한 형태다.

| 새 항목 | 켜고 끄는 것 | 기존 항목과의 관계 |
|---|---|---|
| 진행 단계 | 진행 목록의 "호출 도구 : ○○" 줄. | `tool_names` 이름 변경. |
| 실행 카드 | ⚙ 카드(도구 이름, 실행 중 → 성공/에러 상태). | `tool_arguments`에서 분리. |
| 실행 인자 | 실행 카드 안의 인자 값. 실행 카드가 꺼져 있으면 비활성. | `tool_arguments`에서 분리. |
| 결과 화면 | 성공한 도구가 만든 표·차트·카드. | 신규. 지금은 항상 표시된다. 시작값은 전 그룹 허용. |
| 에러 상세 | 실패 결과 화면과 카드의 "도구 실패 : 내용". 끄면 "도구 실패"만 표시. | `tool_error` 범위 확장. |

- 정보 하나는 항목 하나에서만 켜고 끈다. 도구 이름은 진행 단계와 실행 카드, 에러 내용은 에러 상세에서만 나온다.
- 표시 판정은 `agent.py`에 복사된 다섯 블록을 `can_show(user, feature, tool)` 헬퍼 하나로 합치고, 감사 로그도 그 안에서 남긴다.
- 숨김은 지금처럼 서버에서 보내지 않는 방식을 유지한다.

### 3. 도구와 관계없는 항목은 별도 묶음으로

- 호출 메시지는 "AI 응답 표시" 묶음으로 옮기고 이름을 "답변 스트리밍"으로 바꾼다. 설명에 "끄면 답변이 끝난 뒤 한 번에 표시되고, 도구 호출 전 AI 문장이 있으면 본문 대신 상태바에만 표시됨"을 적는다.
- 대화를 다시 열 때(`build-steps.ts`)도 이 항목의 판정을 따르게 해서 권한 우회를 막는다.
- 도구별 설정 대상에서 뺀다. 문장 하나가 도구 여러 개의 호출에 함께 붙기 때문이다.

### 4. 도구별 화면 정보 표시

- 메인 카드는 지금처럼 항목 × 그룹 표를 둔다. 이 표가 모든 도구에 적용되는 공통 기본값이다.
- 표 아래에 「도구별 세부 조정 >」 버튼을 두고, 누르면 팝업이 열린다.
- 팝업 위쪽에는 도구 드롭다운(도구 표시명), 아래에는 고른 도구의 항목 × 그룹 표가 나온다.
- 팝업 표의 칸은 세 가지 상태(기본 따름 / 표시 / 숨김)를 가진다. 기본 따름 칸은 메인 표의 값을 흐리게 보여주고, 예외를 둔 칸만 진하게 표시한다.
- 드롭다운에서 예외가 있는 도구는 점으로 표시하고, 도구 접근 제어에서 꺼진 도구는 흐리게 표시한다.
- 메인 카드 버튼 옆에 예외가 있는 도구 수를 적는다(예: 「도구별 세부 조정 (2) >」). 팝업을 열지 않아도 예외가 있다는 걸 알 수 있게 한다.
- 팝업에서 바꾼 값은 메인 화면의 저장 배너와 같은 저장·취소 흐름을 탄다.
- 판정은 도구별 예외가 있으면 그 값, 없으면 기본값이다.

```
[메인 카드] 그룹별 화면 정보 표시
항목          admin  user  test
진행 단계       ✓     ✓     ✓
실행 카드       ✓     ·     ✓
...
                         [도구별 세부 조정 (2) >]

[팝업] 도구별 세부 조정
도구: [ 도구 사용 사례 검색 ▾ ]
```

### 5. 메모리 도구: 기능 유지, 표시는 도구별 설정으로

- 메모리 결과(`memory_detailed_results`) 항목은 없애고, 도구 사용 사례 검색의 "결과 화면" 도구별 설정으로 흡수한다. 상태바 한 줄로 대체하는 "요약만" 단계는 두지 않는다(표시 / 숨김 두 단계).
- 도구 안의 분기(`agent_memory.py`)를 없애고 항상 상세 카드를 만들게 한다. 보일지는 공통 판정이 정한다.
- 저장 도구도 결과를 상태바 문구 "Saved to memory" 대신 "메모리에 저장됨: 질문 / SQL" 카드로 바꾸고, 같은 방식으로 도구별 설정을 따른다. 지금은 저장 내용이 접힌 「처리 과정 상세 보기」 속 도구 카드에만 있어서 저장 여부를 알아보기 어렵다.
- 같은 시스템에서 같은 질문이 이미 저장돼 있으면 새로 넣지 않고 시각만 갱신한다(`QdrantAgentMemory.save_tool_usage`). 2026-10-20 테스트에서 "가장 매출이 높은 제품은 무엇인가요?"가 같은 SQL로 3번 저장됐다.

### 6. 메모리 도구 호출 (프롬프트, 작업 중)

- 기반 프롬프트 캐시를 도구 구성별로 나눈다(`DnaSystemPromptBuilder._base`). 도구를 켜고 끄면 프롬프트 속 도구 목록과 메모리 안내도 따라 바뀐다.
- 검색 도구가 등록돼 있으면 파이프라인 맨 앞에 STEP 0(`search_saved_correct_tool_uses` 호출)을 넣는다. 일반·벤치마크 프롬프트 모두 같은 조건(`_pipeline_parts`)을 쓴다. 2026-10-20 테스트에서 호출을 확인했다.
- 저장은 STEP 3으로 넣었지만 모델이 `run_sql` 성공 후 바로 답하고 저장을 부르지 않았다. 강제 문구나 코드 자동 저장은 하지 않기로 했고, 선택형 안내로 바꾸는 방안을 검토 중이다(아래 남은 결정).

## 근거

- 실행 권한과 표시를 한 체크박스가 같이 정하면, 결과를 숨기려고 실행을 막거나 실행을 허용하려고 결과를 노출하게 된다. 둘을 나눠야 각각 의도대로 설정할 수 있다.
- 항목이 겹치면 관리자가 끈 정보가 다른 경로로 보인다. 정보 하나에 항목 하나를 대응시켜야 설정을 믿을 수 있다.
- 도구별 설정을 전체 표가 아니라 예외로 두면, 대부분 기본값을 쓰는 실제 사용 방식에 맞고 화면이 단순하다.
- 메모리 도구는 기존 기능이라 유지해야 하고, 표시 분기를 도구 안이 아니라 공통 판정으로 옮겨야 다른 도구와 같은 규칙으로 관리된다.

## 결과

- **권한 이전.** 결과 화면만 첫 기동 때 전 그룹 허용으로 시작한다. 실행 카드 분리를 하지 않아 `tool_arguments` 복사는 없고, `memory_detailed_results`는 옮기지 않고 지웠다.
- **과거 대화에는 적용되지 않는다.** `SaveComponentsMiddleware`가 그때 보낸 화면을 그대로 저장한다. 카드 설명에 한 줄 적는다.
- **작업 묶음.** 프롬프트 정리까지 한 브랜치(`feat/tool-management`)에 기능 단위 커밋으로 넣고, 두 저장소 PR 하나씩으로 올렸다(백엔드 #186, 웹 #107).
- **영향받는 곳.** 백엔드 `agent.py`, `registry.py`, `config.py`, `group_permissions_service.py`, `agent_memory.py`, `qdrant/agent_memory.py`, `dna_system_prompt_builder.py`. 프론트 `infrastructure-tab.tsx`, `build-steps.ts`.

### 정해진 것 (처음 "남은 결정")

1. 결과 화면 항목은 넣었다. 기본은 전원 허용이다. 처리 과정 블록 안에 보이는 결과 카드(사례 검색·벡터 검색·스키마 조회)도 결과 화면이 정하는 규칙을 유지했다.
2. 저장 도구는 강제 문구·코드 자동 저장·👍 연동 대신 도구 설명을 구체적으로 쓰는 것으로 정했다(언제 쓰는지, `tool_name="run_sql"`, `args={"sql": …}`). 설명을 바꾼 뒤 성공한 SQL이 올바른 형식으로 저장되는 것을 확인했다.

### 프롬프트의 도구 안내 정리 (2026-10-21)

- 시스템 프롬프트 파이프라인 안내를 단계 함수와 "단계 → 필요한 도구" 표(`_PIPELINE_STEPS`)로 나눴다. 도구가 꺼져 있으면 그 도구를 부르라는 문장이 남지 않는다.
- 이전에는 `explore_data`·`describe_schema`·`clarify_request`를 꺼도 안내가 남았다. 이제 각각 빠지거나, 그 도구 없이 읽히는 문장으로 바뀐다.
- 골든 스냅샷은 운영 도구 구성(`describe_schema` 포함 6개)으로 다시 만들었다. 수정 전 골든과 비교해 프롬프트 속 도구 목록 한 줄 외에 차이가 없어, 정리 후에도 운영 프롬프트가 같다는 것이 테스트로 고정된다.
- 시각화 안내(`_viz_guideline_parts`)는 벤치마크 compact에서만 빼는 기존 설계(`test_bench_compact_gates_viz_on_tool`)를 유지했다.

### 함께 발견한 문제 (이 ADR 범위 밖)

- **메모리 도구 정제는 별도 태스크로 한다 (2026-10-21).** 이번 태스크는 도구 관리(두 카드의 역할 분리, 항목 정리, 도구별 표시)에 한정한다. 아래는 그 태스크로 넘긴다.
  - 저장 도구 설명이 저장 대상을 `run_sql`로 한정하고 있어 `visualize_data` 저장까지 막는다. "주로 run_sql, 그 외에는 도구에 넘긴 인자 그대로"로 완화할지 정해야 한다.
  - 메모리 컬렉션 1,143건 중 `run_sql` 1,065건, `visualize_data` 77건, 텍스트 메모리 1건이다. `run_sql` 10건은 `args`가 `{"sql"}` 형식이 아니고, `visualize_data` 기록은 인자 이름이 옛 형식(`x_col`, `y_col`)과 새 형식(`x`, `y`)으로 섞여 있으며 모두 다시 쓸 수 없는 `filename`을 담고 있다.
  - 같은 질문이 매번 새로 저장된다(`uuid4`). 같은 질문이면 갱신하도록 바꿔야 한다.
  - dadap 기반 프롬프트의 "MEMORY SYSTEM" 저장 안내(MUST, 없는 도구 `calculator` 언급)와 우리 STEP 3이 서로 어긋난다.

- 긴 대화(메시지 30~35개 이상)에서 모델이 도구를 부르지 않고 데이터를 지어낸다. 2026-10-20 16:50 답변에서 `run_sql` 없이 입고 이력 표를 만들어 냈다. `HistoryStubFilter`, `ROLLING_DIGEST`와의 관계를 따로 조사해야 한다.
- `DefaultLlmContextEnhancer`가 매 질문마다 텍스트 메모리를 Qdrant에서 검색하지만, 저장 도구(`SaveTextMemoryTool`)가 쓰이지 않아 결과는 항상 0건이다.
- `stream_text_to_ui` 기본값이 `defaults/agent.json`(true)과 코드(`False`)에서 다르다.
- `describe_schema` 호출이 `describe_schema(group="…")<tool_call|>`처럼 깨져 "not found"가 난다. 실패 요청을 그대로 재전송해 재현했고, 프롬프트·도구 설명의 호출 문장 예시를 설명형으로 바꾸면 같은 판단을 정상 형식으로 호출했다. 깨진 호출이 대화 기록에 쌓이면 모델이 계속 따라 한다. 수정은 별도 작업.
- PDF 보고서(`pdf_report_service.py`)는 답변 스트리밍 권한을 적용하지 않고 메시지 문장을 읽는다.
- 설정 메뉴 탭 분류(인프라·파운데이션)가 와닿지 않는다. 5개 탭 재편안을 냈고 별도 작업으로 미뤘다.

# ADR-018: 대화 내 검색어 하이라이트는 렌더링 시 `<mark>`로, 표시는 브라우저 찾기 관례

## 맥락

검색 결과로 대화를 열거나 대화 내 검색 바로 이동할 때, 말풍선 전체 배경만 3.5초 칠해지고 일치한 단어는 표시되지 않았다. 말풍선 안에는 사용자 질문(일반 텍스트), 답변 마크다운, SQL·코드 블록(별도 컴포넌트), 차트·표·수식이 섞여 있어 단어 단위 강조를 어디에 넣을지 정해야 했다. 설계 문서(§11.4)는 이 작업을 "렌더링 경계가 까다로워 별도 개선"으로 미뤄 둔 상태였다.

## 선택지

### 옵션 A: CSS Custom Highlight API (브라우저 찾기 방식)
- **장점:** DOM을 바꾸지 않아 렌더링과 완전히 분리됨. 서식 경계를 넘는 일치(`교체 **비용**`)도 Range 하나로 칠함. 이동·검색어 변경 시 다시 그리기 없음.
- **단점:** `::highlight()`는 배경·글자색·밑줄 정도만 지원(`padding`·`border-radius` 불가). React 밖에서 텍스트 노드를 훑고, 메시지 로드·펼침·재렌더마다 Range를 다시 맞춰야 함. 강조가 DOM에 없어 테스트·디버깅이 어려움. Chrome 105+, Safari 17.2+, Firefox 140+.
- **비용/노력:** 중간. 동기화 로직(MutationObserver 등) 유지보수 부담.

### 옵션 B: 렌더링 시 `<mark>`로 감싸기
- **장점:** 검색창 미리보기의 `<mark>`와 같은 방식·스타일. 모든 브라우저 지원. 결과가 DOM에 있어 테스트 가능. 사용자 질문은 텍스트 분할, 답변 마크다운은 기존 `rehypePlugins`에 플러그인 하나 추가로 끝남(코드·수식은 건너뜀).
- **단점:** 서식 경계를 넘는 일치는 못 칠함. 검색어가 바뀌면 일치한 말풍선의 마크다운을 다시 파싱함.
- **비용/노력:** 낮음.

## 결정

**옵션 B를 선택한다.** 표시는 브라우저 찾기 관례를 따른다. 대화 전체의 일치 단어는 노랑(`bg-yellow-300`), 지금 `‹ ›`로 가리키는 말풍선의 일치 단어는 주황(`orange-400`), 글자는 라이트·다크 모두 검정, 사각형·여백 없음.

## 근거

- 다시 그리기 비용 실측: 표 2개가 든 1,670자 답변 기준 하이라이트 없이 2.98ms, 있을 때 3.57ms. 개발 DB 대화당 메시지는 중앙값 2, 상위 1% 5, 최대 759로, 지금은 대화를 열 때 모든 메시지를 그리므로 재파싱 비용은 "대화를 한 번 더 여는 것"보다 작다.
- "현재 위치" 표시는 말풍선 바깥 요소의 `data-search-current` 속성과 Tailwind `group-data-[search-current]/search-message:` 선택자로만 바꿔, `‹ ›` 이동 시에는 마크다운을 다시 그리지 않는다.
- 처음에는 구현 안전성 때문에 옵션 A를 제안했지만, 퍼블리싱 관점(검색창과 같은 스타일, 디버깅 가능성)에서 다시 따져 B로 바꿨다. 이후 사각형·여백 없는 스타일로 정해져 A의 스타일 제약은 사라졌지만, DOM 동기화 비용이 여전히 더 크다고 판단했다.

## 결과

- 서식 경계를 넘는 일치와 NFD로 저장된 본문은 하이라이트가 빠질 수 있다(스크롤 이동은 정상).
- SQL·코드 블록(별도 컴포넌트)은 칠하지 않는다.
- 재검토 시점: 아주 긴 대화에서 검색 바를 열 때 멈칫한다는 피드백, 또는 서식 경계 누락이 실제 불편으로 보고될 때 옵션 A로 이전 검토.
- 영향 컴포넌트: `chat-view.tsx`(검색어 context·현재 표시), `chat-message.tsx`(텍스트·마크다운 하이라이트), `search-highlight.tsx`(공용 `<mark>`), `lib/search-matches.ts`(`splitSearchText`·`rehypeSearchHighlight`).

# ADR-002: 공통 경로(mail2task_paths.yml)에 키별 local/cloud 타입 도입 + 활성 파일 고정 경로 보관

> 대상: mail2task / mail2task-config 스킬의 공통 경로 설정 `mail2task_paths.yml`.

## 맥락

mail2task 파이프라인은 결과·로그·회신초안·제외목록·입력 .eml 등 6종 폴더 위치를 공통 경로
파일 `mail2task_paths.yml`(6키: config·task_results·reply_drafts·except_results·logs·eml_inbox)로
관리한다. 이 파일을 **파싱하는 코드는 없고**, 경로 해석은 LLM이 `interface.md` A-3 규칙대로 수행한다.

기존 스키마(v2.0)는 **드라이브 전용**이었다 — 각 키가 `{drive, drive_id}`만 갖고, 해석은
"drive_id 있으면 ID로, 없으면 이름으로" 하나뿐. 과거 v1.0의 `storage/local` 하이브리드 필드는
의도적으로 제거된 상태였다.

문제 두 가지:
1. **로컬 맥은 구글드라이브가 마운트**돼 있어 Drive MCP·base64 디코딩 없이 마운트 경로를 직접
   읽고 쓸 수 있는데, 드라이브 전용 스키마는 이 빠른 경로를 못 쓴다. 드라이브 커넥터는 **in-place
   덮어쓰기가 없어** 같은 이름 사본이 누적되는 고질적 문제도 있었다.
2. 활성 `mail2task_paths.yml`을 팀 공유 드라이브 1개로 두면, **로컬 경로는 머신마다 다르므로**
   사용자별 설정과 충돌한다.

## 선택지

### 타입 지정 단위
- **옵션 A: 키마다 개별 타입(local/cloud)** — 6키를 각각 독립 지정. 유연(결과는 로컬, 공유 config는 드라이브).
- 옵션 B: 전역 기본 + 키별 예외 / 옵션 C: 전역 하나만(혼용 불가).

### 활성 파일 보관 위치
- **옵션 A: 스킬 밖 고정 경로** — 재배포·이름변경에 안전, 개인 경로 유출 없음, 런타임 데이터/스킬 로직 분리.
- 옵션 B: 스킬 디렉토리 안 — 한곳에 모이나 스킬 재설치 시 덮어쓰기·공유 시 개인 경로 노출 위험.

## 결정

1. **타입 = 키마다 개별.** 각 키에 `type: cloud`(구글드라이브) | `type: local`(로컬 파일시스템).
   생략 시 `meta.default_type`(기본 `cloud`). → **기존 v2.0 파일과 하위호환**(type 없으면 전부 cloud).
2. **활성 파일 = 스킬 밖 고정 경로** `~/.claude/mail2task/mail2task_paths.yml`.
   env `MAIL2TASK_HOME`로 override 가능. 스킬 안 `assets/paths.template.yml`은 **템플릿**일 뿐이고,
   채워진 실값은 config 스킬이 만드는 **산출물**이라 스킬 밖에 둔다.
3. 클라우드(구글드라이브)는 일단 gdrive만. 코워크용 별도 경로 파일은 범위 밖.

## 현재 로직 (결정 후)

### 스키마 v3.0
```yaml
meta:
  version: "3.0"          # 3.0=키별 타입 · 2.0=drive-only · 1.0=hybrid
  drive_root: "Mail2Task"
  local_root: ""          # (선택) local 키 상대경로 기준
  default_type: "cloud"   # 키에 type 없을 때
paths:
  task_results:
    type: cloud            # cloud | local (생략 시 default_type)
    drive: "Mail2Task/Task_List"   # type=cloud 일 때
    drive_id: ""
    local: ""                      # type=local 일 때 (절대경로·~·local_root 기준)
  # config / reply_drafts / except_results / logs / eml_inbox 동일
```
- 각 항목은 cloud(`drive`/`drive_id`)·local(`local`) 필드를 **모두 보유**하되 `type`에 해당하는
  것만 사용 → 타입 전환 시 반대편 위치값 보존(안전).

### 경로 해석 (LLM — interface.md A-3)
- effective_type = `entry.type` 없으면 `meta.default_type`.
- **cloud:** drive_id→drive 로 Drive 커넥터(다운로드 base64=A-3.2, 업로드 create_file+parentId=A-3.1).
- **local:** `local` 경로 직접 read/write — Drive MCP·base64 불필요, **in-place 덮어쓰기 가능**.

### 활성 파일 로드 순서
1. `$MAIL2TASK_HOME/mail2task_paths.yml` (env 설정 시)
2. `~/.claude/mail2task/mail2task_paths.yml` (기본·정본)
3. 드라이브 `Mail2Task/Config` 사본 (클라우드 폴백)

### 검증 (mail2task-config/scripts/validate_paths.py)
- type=cloud → `drive` 필수 / type=local → `local` 필수 / `type` 값은 cloud·local 만.

## 수정으로 나아진 점

- **속도:** local 키는 마운트 경로 직접 read/write → Drive 다운로드·base64 디코딩 0회.
- **사본 누적 해소:** local은 in-place 덮어쓰기 가능 → "동명 사본 최신 1개" 문제가 local 키에선 사라짐
  (cloud 키만 해당). 결과/로그를 로컬에 두면 드라이브가 깨끗해진다.
- **유연성:** 결과·로그는 로컬, 공유 config는 드라이브 식으로 키별 최적 배치. 타입 전환은 `type` 한 줄만.
- **안전한 보관:** 활성 설정을 스킬 밖 고정 경로에 둬 스킬 재배포·이름변경에 안전, 개인 로컬 경로 유출 없음.
- **하위호환:** 기존 v2.0(드라이브 전용) 파일은 수정 없이 그대로 동작(전부 cloud로 간주).

## 결과 (트레이드오프 · 주의)

- **local 은 로컬 머신 전용.** 챗(클라우드 샌드박스)은 매 세션 새 VM이라 로컬 경로·고정 경로가 없다 →
  클라우드 실행에서 어떤 키가 local 이면 그 키는 서빙 불가(보고 후 cloud 권장). 그래서 cloud 폴더
  골격·드라이브 사본을 폴백으로 유지한다.
- 팀 공유는 cloud 키 + 드라이브 폴더 단위로 유지(활성 파일 자체는 사용자별).
- 검증 완료: 혼합 생성 OK / v2.0 하위호환 OK / 음성 케이스(local·cloud 위치 누락·잘못된 type) FAIL.

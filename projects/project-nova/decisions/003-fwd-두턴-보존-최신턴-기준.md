# ADR-003: FWD 메일은 "두 턴 보존 + 최신 턴 기준"으로 처리 (top_comment 비손실)

> 대상: mail2task 스킬 `stages/00-ingest/scripts/ingest.py`(`build_input`) ·
> `assets/rules.yml`(`forward_markers`) · `scripts/pipeline.py --new` · `scripts/run_pipeline.py prep`.
> **구현 상태: 구현 완료(2026-06-19). 실제 코퍼스(A/B/C) + 합성(D) 검증 통과.**

## 맥락

데모 운영은 실제 고객 메일을 `dna.mail2task@gmail.com` 으로 **전달(FWD)** 해 파이프라인에 먹인다.
`00-ingest`는 본문을 첫 FWD/인용 경계로 가른다:

- **`top_comment`** = 경계 위 = **이번에 새로 쓴 글**(회신 본문 / 전달하며 단 지시)
- **`body_main`** = 경계 아래 = **인용된 이전 메일 본문**
- **`forwarded_origin`** = 인용 원본 헤더(발신·제목·날짜)

그런데 `build_input()` 이 두 가지를 한다:
1. **demo 모드면 메타(`sender/subject/date`)를 `forwarded_origin`(옛 발신자)으로 치환.**
2. **`input.body` 는 모드와 무관하게 항상 `body_main`(인용된 옛 메일).** → **`top_comment`(이번에 쓴 새 글)를 `input`에서 통째로 버린다.**

```python
# ingest.py build_input() — 문제 지점
meta = origin if (mode == "demo" and origin.get("sender")) else envelope
return { "subject": meta.get("subject") ..., "body": body_main, "sender": meta.get("sender") ... }
#                                                  ^^^^^^^^^ 항상 옛 메일. top_comment 누락.
```

게다가 `rules.yml` 의 `default_mode: demo` 가 **하드 고정**이라, `suggest_mode()` 휴리스틱(상단 코멘트가
실질적이면 pilot로 보내는 분기)이 **무력화**된다 — 모든 메일이 demo로 강제된다.

### 증상 (2026-06-19 KAC 배치 실측)

| 메일 | 실제(envelope) | `input.sender`(demo 치환) | `input.body` | 잃은 것 |
|------|------|------|------|------|
| 우리측 회신(Re:) | 전채린(우리) | **윤혜영(고객)** | 윤혜영 원 요청 | 우리 회신문(top_comment) |
| 고객 회신+새요청(RE:) | 김충현(고객) | (origin 파싱 실패→envelope 폴백) | **직전 전채린 회신** | 고객 새 요청(top_comment) — 22만건·엑셀버그 |

→ **모든 스레드 후속 메일이 "직전 턴"을 본문으로 오인**한다. nature·요약·업무·채번이 줄줄이 꼬인다.
오늘 결과가 맞은 건 순전히 `run_pipeline.py prep` 의 `judgment_request` 가 `top_comment`·`envelope` 를
**따로** 실어 사람(LLM)이 그걸 읽었기 때문이다. **결정론 스크립트나 비-prep `--new` 경로는 top_comment를 잃는다.**

> 선행 임시조치(밴드에이드): prep 이 envelope/top_comment 동봉([[projects/project-nova/troubleshooting/mail2task-re-mail-our-reply-misdetection|Re: our_reply 미인식]]),
> 성격 판정에 "서명 우선" 규칙 추가([[projects/project-nova/issues/fwd-sender-our-reply-misclassification|FWD sender 오분류]]),
> prep dedup을 envelope 기준으로 우회. 모두 **판단 레이어 보정**일 뿐 ingest의 데이터 손실 자체는 그대로다.

## 핵심 진단

demo는 "전달된 샘플 → **안쪽 원본**이 진짜 메일"이라고 가정한다. 이건 **신규 고객 메일을 한 번 전달**한
경우에만 맞다. **회신 체인을 전달**하면 정작 처리할 **최신 턴(top_comment)** 이 아니라 **가장 깊은 옛 원본**을
집는다. 고장의 본질은 *메타 치환*이 아니라 **`body = body_main` 으로 top_comment를 버린 것**이다.

## 선택지

### 옵션 A: 최신 턴으로 swap (top_comment를 body로 교체)
- **장점:** 회신/추가요청은 맞게 본다.
- **단점(치명):** **전달+지시("이렇게 해주세요~") 케이스가 터진다.** 처리할 원본 내용은 body_main에 있는데
  top_comment(지시)만 보고 **원본 요청을 통째로 놓친다.** ← 사용자가 우려한 바로 그 케이스.

### 옵션 B: our_reply만 특수처리
- **장점:** 변경 최소.
- **단점:** envelope=우리+Re: 만 구제. **고객이 회신하며 새 요청(고객_addition)** 케이스는 여전히 옛 본문을 봄.

### 옵션 C: default_mode를 auto로 복귀
- **장점:** 가장 작은 변경. 메타는 메일마다 demo/pilot 자동 판정.
- **단점:** `input.body = body_main` 문제는 **그대로**(pilot도 body는 body_main). 부분 해결.

### 옵션 D: 두 턴 보존 + 최신 턴 기준 (채택)
- 어느 턴도 버리지 않는다. `input` 에 **현재 턴(top_comment)** 과 **인용 원본(body_main)** 을 **둘 다 라벨링**해
  싣고, 성격·업무 판정은 `envelope.sender`(실제 작성자) + 내용으로 한다.
- **장점:** C·D(순수전달·전달지시)는 영향 없이 그대로, A·B(스레드 회신)만 고쳐진다. 손실 0.
- **단점:** ingest 출력 스키마·`--new` 입력·하류 단계(`input.body` 참조처) 동시 손질 필요(범위 큼).

## 결정

**옵션 D — 두 턴 보존 + 최신 턴 기준.**

"최신 턴 재정의"는 *"body_main을 top_comment로 바꾼다"* 가 아니라 **"top_comment를 안 버린다(두 턴 다 보존)"** 이다.

### 케이스별 거동 (정본)

| 케이스 | top_comment | body_main | 처리 대상 | 판정 |
|--------|-------------|-----------|-----------|------|
| **C. 순수 전달** (FYI/"전달드립니다"/빈칸) | 거의 없음 | 원본 고객 요청 | **원본(body_main)** | top_comment trivial → 현 demo대로. 영향 없음 |
| **D. 전달+지시** ("이렇게 해주세요~","견적 좀") | 얇은 지시 | 원본 고객 요청 | **원본(body_main)=업무** + 지시(top_comment)는 우선순위·담당 힌트로 **병합** | 원본 안 놓침 |
| **A. our_reply** (envelope=우리) | 우리 처리내용 | 고객 원 요청(맥락) | 기존 (이슈,트래킹) 행 **처리내용 갱신** | top_comment=처리내용, 새 채번 X |
| **B. 고객 회신+새요청** (envelope=고객) | 고객 새 요청 | 직전 턴(맥락) | **새 트래킹/이슈** | top_comment=업무, body_main=맥락 |

- **demo의 "안쪽 원본을 본다"는 본능은 C·D에선 그대로 옳다.** 고장난 건 A·B에서 top_comment를 버린 것뿐.
  두 턴을 다 보존하면 C·D는 무영향, A·B만 교정된다.
- **C vs D 구분 신호:** `top_comment` 실질성(길이/요청문 여부). **A vs B 구분 신호:** `envelope.sender` 도메인(우리 vs 외부).

## 구현 내역 (2026-06-19 적용)

| 구분 | 파일 | 변경 |
|------|------|------|
| ingest | `stages/00-ingest/scripts/ingest.py` `build_input` | `input` 에 두 턴 필드 추가(`current_turn`=top_comment, `quoted_origin`=body_main) + `envelope`/`forwarded_origin`/`forwarded` 동봉. **`body` 는 두 턴을 섹션으로 합쳐 무손실**(현재 턴 + "----- (이전/인용 메일) -----" + 인용 원본). 메타 치환은 **`is_reply_subject()`(Re:/회신/답장)** 로 분기 — **회신이면 envelope(실제 작성자)**, 순수/지시 전달(Fwd)이면서 demo면 forwarded_origin. |
| ingest | `stages/00-ingest/assets/rules.yml` `forward_markers` | "원본 메일/Original Message" 구분선 마커를 `[-─—=_]{2,}` 로 확장 — **하이픈뿐 아니라 박스문자(─)·전각대시 구분선**도 전달 경계로 인식(한국 웹메일 D 케이스 감지). |
| pipeline | `scripts/pipeline.py` `cmd_new` | `--stdin` input 에서 `current_turn`/`quoted_origin`/`envelope`/`forwarded_origin`/`forwarded` 를 state.input 으로 승계(기존 화이트리스트가 버리던 것 보존). |
| prep | `scripts/run_pipeline.py` | judgment_request 의 `input` 화이트리스트에 `current_turn`/`quoted_origin` 추가 → 판단이 최신 턴을 정식 필드로 본다. |

> **`default_mode: demo` 고정은 유지.** `is_reply_subject` 분기로 demo가 회신(A·B)을 올바르게 처리하므로
> default_mode를 풀 필요가 없어졌다(범위·리스크 축소). 회신은 envelope, 전달은 demo 메타치환이 그대로 공존.

## 검증 (2026-06-19)

| 케이스 | 입력 | 결과 |
|--------|------|------|
| A. 원본 신규 | 인포그래픽 확인요청.eml | `forwarded=False`, `input.sender=윤혜영`, body=원 요청 (변화 없음) ✓ |
| B. our_reply | Re_ 인포그래픽 확인요청.eml | `input.sender=전채린(우리)` ← **교정**(이전 윤혜영), `current_turn`=우리 회신 ✓ |
| C. 고객 회신+새요청 | RE_ Re_ …수정요청.eml | `input.sender=김충현`, `body`가 **고객 새 요청부터** 시작(이전엔 인용된 전채린 회신) ✓ |
| D. 전달+지시(합성) | Fwd: 견적 요청 | `forwarded=True`(─ 마커), `current_turn`=지시, `body`에 지시+원요청(20석·납품) **모두 보존** ✓ |
| dedup | 회신 재처리 | 이미 Log에 있는 RE: 수정요청만 중복 제외, our_reply는 통과(정상) ✓ |

> **남은 한계:** `parse_origin_header` 가 라벨 없는 인용 헤더(`"이름" <메일>` 단독 줄)에서 발신자 추출에 실패할 수 있어
> D 케이스의 `input.sender` 가 원 요청자 대신 전달자(envelope)로 잡힐 수 있다. **단 본문(body)에는 원 요청이 보존**되어
> 내용 손실은 없다(꼬임의 핵심은 해소). 헤더 파서 강화는 후속 과제.

## 결과 (트레이드오프 · 주의)

- **D 케이스 안전 확보**가 이 결정의 존재 이유 — 단순 swap의 함정을 피한다.
- 범위가 ingest→pipeline→단계까지 걸쳐 **한 번에 손봐야** 회귀가 없다(부분 적용 시 일부 경로만 고쳐져 더 헷갈림).
- **하위호환:** `input.body` 는 유지(기존 단계 안 깨짐). 새 단계만 두 턴 필드를 추가로 읽는다.
- 재검토 시점: 구현 후 KAC 7건+이번 3건 회신 배치 재처리로 A·B·C·D 전부 검증.
- 선행 밴드에이드(서명 우선 규칙·prep envelope 동봉·dedup 우회)는 이 결정이 구현되면 **데이터 레이어로 흡수**되어
  판단 레이어 보정 의존이 줄어든다(완전 제거는 아님 — envelope 기준 판정은 계속 유효).

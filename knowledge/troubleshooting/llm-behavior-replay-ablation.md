# LLM 이상 동작은 실패한 요청을 그대로 재전송하고 요소를 하나씩 빼서 좁힌다

## 증상

LLM이 가끔 이상하게 동작한다. 도구 호출 형식이 깨지거나, 지시를 무시하거나, 답을 지어낸다. 로그를 보면 "어떤 프롬프트 변경 이후로 늘었다" 같은 상관관계가 보여서 그걸 원인으로 단정하기 쉽다.

## 함정

- **상관관계는 원인이 아닙니다.** dna-sql-agent에서 `describe_schema` 호출이 깨지는 비율이 "메모리 안내가 들어간 뒤 3% → 67%"로 보였습니다. 그런데 표본이 6턴이었고, 실제 원인은 다른 곳에 있었습니다.
- **직접 만든 짧은 질문으로는 재현되지 않는 경우가 많습니다.** 실제 실패는 긴 시스템 프롬프트, 앞선 대화, 도구 결과가 겹친 상태에서 일어납니다. 비슷한 질문 12개를 보냈을 때 모두 정상이었습니다.
- **판단 자체가 달라지는 경우가 있습니다.** 요소를 빼면 모델이 아예 다른 도구를 고르기도 하는데, 이건 "고쳐졌다"가 아니라 "판단할 수 없음"입니다. 같은 판단(같은 도구, 같은 대상)을 하면서 형식만 고쳐졌을 때를 효과로 칩니다.

## 방법

1. **복원:** 실패한 턴의 요청 전체를 로그에서 복원합니다. 시스템 프롬프트, 메시지, 도구 정의가 모두 필요하므로 요청 로그(예: `FileLoggingMiddleware`)가 이걸 남겨야 합니다.
2. **조건 맞추기:** 운영과 같은 조건으로 보냅니다. 스트리밍 여부, `temperature`, 생각 모드, 벤치마크 모드 같은 프롬프트 분기까지 맞춥니다.
3. **재현 확인:** 원본 그대로 여러 번 보내서 재현되는지 먼저 확인합니다. 재현이 안 되면 그다음 단계는 의미가 없습니다.
4. **하나씩 빼기:** 의심 요소를 **하나씩** 빼거나 바꾼 변형을 같은 횟수만큼 보내고 결과를 표로 비교합니다.
5. **일반화 확인:** 찾은 수정을 다른 실패 요청에도 적용해 봅니다.

## 결과 사례

| 변형 | 결과 |
|---|---|
| 원본 그대로 | 3/3 깨짐 (재현) |
| 메모리 안내·도구 전부 제거 | 3/3 정상 |
| 메모리 문구만 제거 | 여전히 깨짐 → 메모리 안내는 원인 아님 |
| `describe_schema` 호출 문장 예시만 설명형으로 | **같은 판단을 정상 형식으로 3/3** |

## 주의

- 사용자 대화가 들어간 요청은 원래 쓰던 LLM 서버로만 보냅니다(외부로 보내지 않음).
- `temperature 0`이어도 서버 일괄 처리 때문에 결과가 조금씩 달라질 수 있어서, 변형마다 여러 번 보냅니다.

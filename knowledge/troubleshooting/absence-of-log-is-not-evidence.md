# 로그가 안 찍힌 것을 근거로 쓰기 전에, 그 로그가 찍히는지부터 확인

## 증상

"이 분기에 로그를 넣어뒀는데 안 찍혔다 → 그러니까 이 코드는 실행되지 않았다"는
추론이 틀리는 경우. 실제로는 코드가 실행됐는데 **로그가 그 파일에 도달하지 않는**
것이었다.

## 원인

로거가 출력에 도달하지 못하는 경로는 여러 가지다:

- 모듈 로거의 레벨이 `INFO` 인데 핸들러/루트 레벨이 `WARNING` 이상
- 애플리케이션이 특정 로거만 파일 핸들러에 연결하고 나머지는 콘솔로만 보냄
- 로그 파일이 회전(rotate)돼 확인한 파일에는 없음
- 실행 중인 프로세스가 로그를 넣기 **전 버전**의 코드로 기동돼 있음

## 확인 방법

**같은 파일에 이미 찍히고 있는 로그를 대조군으로 삼는다.**

```
# 동작이 확인된 다른 INFO 로그가 이 파일에 있는가?
grep -c "동작 확인된 로그 문구" log/app.log
```

대조군이 0이면 그 파일에 그 레벨의 로그가 애초에 안 찍히는 것이므로,
내 로그의 부재는 아무것도 증명하지 못한다.

**부재 대신 존재를 근거로 삼는 것이 낫다.** 예를 들어 요청/응답 덤프처럼 이미
확실히 기록되는 데이터에서 원하는 값을 직접 확인한다. 실제로 이 방법으로
`user.metadata` 내용을 확인해 코드가 정상 동작 중임을 증명할 수 있었다.

## 함께 주의할 것

**프로세스 기동 시각과 파일 수정 시각을 비교한다.**

```
stat -f "%Sm" -t "%H:%M:%S" src/module.py     # 수정 시각
ps -eo lstart,command | grep "[m]ain.py"      # 기동 시각
```

수정이 기동보다 나중이면 실행 중인 코드는 옛 버전이다. "고쳤는데 안 된다"의
상당수가 이것이다.

## 교훈

부재(negative evidence)는 **관측 수단이 동작한다는 전제** 위에서만 근거가 된다.
그 전제를 먼저 검증하지 않으면, 틀린 결론 위에 계속 추론을 쌓게 된다.

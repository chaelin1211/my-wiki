# 도커 빌드 컨텍스트는 클라이언트가 읽어 전송한다 — 원격 데몬이어도 소스는 로컬에 필요

## 한 줄

`DOCKER_HOST=ssh://...` 로 원격 데몬을 써도, `docker build <경로>` 의 그 경로는
**`docker` 명령을 실행하는 쪽 파일시스템**에서 읽힌다. "데몬이 서버에 있으니
소스도 서버가 알아서 찾겠지" 는 성립하지 않는다.

## 왜

빌드 컨텍스트는 데몬이 경로를 열어보는 것이 아니라, **클라이언트가 그 디렉토리를
tar 로 말아 데몬에 전송**하는 구조다. 데몬 입장에서 그 경로는 존재조차 모른다.

| | 데몬 위치 | 소스가 있어야 하는 곳 |
|---|---|---|
| 로컬 도커 | 내 PC | 내 PC |
| `DOCKER_HOST=ssh://server` | 원격 서버 | **여전히 내 PC** |
| CI (self-hosted runner) | 러너 | 러너 워크스페이스 |

## 어디서 걸리나

CI 에서 "이미 서버에 이미지가 있으니 소스 체크아웃은 빼도 되지 않나?" 라는 판단이
나올 때. 두 경우를 구분해야 한다.

- **기존 이미지를 묶기만 함**(`docker save`, `docker tag`) → 소스 **불필요**.
  이미지가 데몬에 있기만 하면 된다
- **빌드함**(`docker build`) → 소스 **필요**. 데몬 위치와 무관

즉 "빌드 옵션은 남기고 소스 체크아웃만 뺀다" 는 조합은 성립하지 않는다.
옵션을 켜는 순간 실패한다.

## 관련

- 빌드와 패키징의 책임을 분리하면 이 혼동 자체가 사라진다 — 빌드는 소스 저장소의
  워크플로가, 묶는 일은 배포 저장소의 워크플로가 맡고, 후자는 항상 `--no-build`

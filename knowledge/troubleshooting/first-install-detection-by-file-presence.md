# 최초 설치 판정을 파일 존재로 하면 업그레이드에서 빠진다

## 증상

- 새로 설치한 환경에서는 초기 데이터(기본 권한·기본 설정·시드 레코드)가 잘 들어간다
- **이미 돌던 환경을 새 버전으로 올리면** 같은 초기 데이터가 들어가지 않는다
- 에러도 경고도 없다. 그냥 조용히 건너뛴다
- 나중에 만든 대상(새 그룹·새 테넌트)은 정상적으로 받아서, "새로 만든 건 되는데 원래 있던 건 안 되는" 비대칭이 생긴다

## 원인

초기화 코드가 "최초 설치인가" 를 **설정 파일이나 디렉터리의 존재 여부**로 판정한다.

```python
first_install = not (config_dir / "app_config.json").exists()
...
if first_install:
    mark_everything_for_seeding()
else:
    mark_only_newly_added_items()
```

이 판정은 두 상태를 구분하지 못한다.

| 실제 상태 | 파일 존재 | 판정 | 원하는 동작 |
|---|---|---|---|
| 진짜 최초 설치 | 없음 | 최초 ✅ | 전량 시딩 |
| 시딩 로직이 없던 구버전으로 이미 뜬 환경 | **있음** | 최초 아님 ❌ | 전량 시딩이 필요한데 안 함 |

특히 **설정 디렉터리를 영속 볼륨으로 마운트하는 배포**에서 확실하게 걸린다. 컨테이너를 새로 말아 올려도 볼륨의 파일이 남아 영원히 "최초가 아님" 이 된다. 시딩 로직 자체를 나중에 추가한 경우, 그 로직은 **정작 필요한 기존 환경에서만 안 도는** 상태가 된다.

## 해결

**판정 기준을 "부수적 흔적" 이 아니라 "결과물의 유무" 로 바꾼다.** 파일이 있느냐가 아니라, 넣으려는 데이터가 실제로 있느냐를 본다.

```python
# ✗ 파일 존재로 추론
first_install = not config_file.exists()

# ✓ 목표 상태를 직접 확인 (멱등)
already_seeded = await db.fetchval("SELECT 1 FROM permissions WHERE item_key = $1", key)
if not already_seeded:
    await seed(key)
```

값을 지운 상태와 한 번도 넣지 않은 상태를 구분해야 한다면(관리자가 일부러 뺀 권한이 재기동 때 되살아나면 안 되는 경우), **추론하지 말고 사실을 기록한다** — 시딩 완료 표식을 DB 에 남기고 그걸 본다. 표식을 쓸 때 지켜야 할 것:

- **표식은 성공했을 때만 소진한다.** 대상이 0건이라 아무것도 못 넣었는데 표식만 지우면 두 번 다시 복구되지 않는다.
- **표식을 데이터와 같은 저장소에 둔다.** 표식은 파일에, 데이터는 DB 에 두면 둘이 어긋난다.

## 예방책

- 마이그레이션·시딩은 **"몇 번 돌려도 같은 결과"** 를 기준으로 설계한다. "처음인가?" 라는 질문 자체가 대개 불필요하다.
- 신규 생성 경로(새 그룹·새 테넌트)와 부트스트랩 경로(설치 시 SQL 로 직접 INSERT 되는 기본 레코드)가 **같은 초기화 함수를 지나는지** 확인한다. 부트스트랩만 다른 길로 가면 이 비대칭이 그대로 생긴다.
- 업그레이드 시나리오를 실제로 시험한다. 새 설치만 시험하면 이 결함은 절대 드러나지 않는다.

# LLM이 만든 입력이 틀리면 고치지 말고 "대신 쓸 형태"와 함께 거절

## 문제

LLM이 도구 입력(SQL, 식별자 등)을 대상 시스템이 받지 못하는 형태로 만든다. 오류 문구에 무엇을 바꿔야 하는지가 없으면 LLM은 철자·형태만 바꿔 같은 실패를 반복하며 호출 횟수를 소모한다.

## 패턴

1. **검증 단계에서 거절:** 실행 전에 막는다. 실행 SQL은 항상 LLM 원본과 같게 유지해 감사·기록이 일관된다.
2. **오류 문구에 대체 형태를 명시:** "X is not supported; use Y instead". 고쳐도 소용없는 재시도(예: 철자 바꾸기)는 하지 말라고 함께 적는다.
3. **반복 실수는 프롬프트로 선제 차단:** 거절 안내는 그 대화 안에서만 학습된다. 새 대화마다 같은 실수가 나면 현재 대상에 해당하는 규칙 한 줄만 프롬프트에 넣는다.
4. **재시도를 막지 말고 방향을 준다:** 일시적 원인(다른 연결로 재시도하면 성공)이 있을 수 있으면 "한 번 재시도, 그래도 실패하면 이렇게"로 안내한다.

## 자동 보정을 피하는 이유

- 실행된 것과 LLM이 쓴 것이 달라져 원본이 모호해진다.
- LLM이 실수를 계속한다.
- 의미가 미묘하게 다른 경우(예: OFFSET이 0부터 vs 1부터)를 놓치기 쉽다.
- "이것도 고치자"로 범위가 번진다.

로그로 재시도 낭비가 계속 확인될 때만 의미가 같은 좁은 범위의 자동 보정을 검토한다.

# 정적 HTML 하니스로 DB/백엔드 없이 프론트 로직만 실제 라이브러리로 검증하기

## 언제 쓰나

- 고쳐야/검증해야 할 버그가 순수 프론트엔드 로직(엑셀 생성, 차트 렌더링, 폼 검증 등)에 있는데,
- 그 화면이 로딩되려면 백엔드 API/DB 연동이 먼저 성공해야 하고,
- 그 DB/API가 로컬에서 접속 불가(내부망 전용, VPN 필요, 인증 필요 등)인 상황.

이럴 때 "DB 연결을 어떻게든 뚫는다" 대신, 문제되는 로직만 떼어내서 실제 프로덕션 JS/라이브러리를 그대로 로드하고 하드코딩된 샘플 데이터를 주입하는 독립 HTML 페이지를 만드는 게 훨씬 빠르다.

## 방법

1. 문제 화면이 로드하는 JS 파일들을 추적해서, 실제 버그가 있는 함수가 어떤 라이브러리(예: 그리드, 엑셀 생성기)와 어떤 공용 유틸(`commonLib.js` 류)에 의존하는지 파악한다.
2. 새 정적 HTML을 만들어 그 JS/CSS 파일들을 **원본 그대로** `<script src>`로 로드한다 (복사·수정하지 않음 — 그래야 실제 버그/수정을 그대로 검증할 수 있음).
3. 화면의 데이터 그리드/테이블이 서버에서 받는 응답과 동일한 필드 구조를 가진 샘플 데이터를 하드코딩한다 (2~3행이면 충분).
4. 문제되는 버튼 핸들러(예: 엑셀 다운로드 클릭 핸들러)를 운영 코드와 동일하게 복사해 붙이고, 그 안에서 그리드 객체와 샘플 데이터를 사용하게 연결한다.
5. 이미 로컬에 애플리케이션 서버(embedded Tomcat 등)가 떠 있다면, 재빌드 없이 실제 배포된 exploded 디렉토리(`target/.../webapps/...`)에 이 HTML 파일을 직접 복사해서 바로 서빙되게 한다.
6. 브라우저로 열어서 버튼을 눌러보고, 콘솔 에러 / 실제 다운로드된 파일(내용까지) 등을 확인한다.
7. **버그 재현도 같이 해볼 것**: 수정 전 상태(버그 있는 코드)로 잠깐 되돌려서 동일한 하니스로 눌러보면, "진짜 그 원인이 맞았는지"와 "수정이 그 문제를 실제로 없앴는지"를 대조 확인할 수 있다.

## 예시

`kacportal`의 스마트기기 이용통계 화면 — Altibase DB가 로컬에서 접속 불가라 화면 자체가 로딩 단계에서 멈추는 상황. `commonLib.js`(엑셀 생성 유틸)와 `Tabulator`, `ExcelJS`를 그대로 로드하고, `AIRPORT`/`QUARTER`/`MONTH`/`BIO_USER_CT_KE` 등 실제 응답과 동일한 필드명의 샘플 데이터 2행을 하드코딩해서 엑셀 다운로드 버튼만 독립적으로 테스트. `sheetName` 누락 버그를 재현(에러 재현, 파일 미생성 확인)하고 수정(파일 생성 + 시트명 확인)까지 실제 라이브러리로 end-to-end 검증함.
→ [[projects/kacportal/issues/smdevc-smart-statistics-excel-download-sheetname-missing]]

## 주의할 점

- 하니스 페이지는 프로덕션 코드가 아니므로 git에 커밋하지 않거나, 커밋하더라도 명확히 "임시/테스트용"임을 표시한다.
- 라이브러리 초기화가 비동기인 경우(예: Tabulator는 `new Tabulator()` 직후 DOM이 아직 준비 안 됨) 하니스에서도 동일한 타이밍 문제가 재현되니, `tableBuilt` 같은 준비 완료 이벤트를 기다려야 한다 — 이것도 실제 버그를 놓치지 않기 위해 원본 코드의 타이밍을 그대로 따라가는 게 중요하다.
- 목적은 어디까지나 "프론트 로직만" 검증하는 것. 서버 연동/인증/DB 쿼리 자체의 정상 동작까지 이 방법으로 증명할 수는 없다.

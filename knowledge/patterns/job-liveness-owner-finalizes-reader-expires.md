# 비동기 작업 정리 — 끝내는 건 실행 주체, 죽음 판정은 읽는 쪽이 생존 신호로

## 문제

요청을 받은 워커가 백그라운드 작업(`asyncio.create_task`)을 실행하고 상태를 DB 작업 행에 남기는 구조에서, "오래된 `running` 작업"을 **경과 시간**으로 정리하면 두 오판이 항상 함께 생긴다.

- 기준보다 오래 걸리는 **정상 작업을 실패 처리** — 바깥에서 DB 상태만 `error`로 바꾸고 실제 작업은 계속 돌아 결과는 쌓이는데 화면은 실패
- **죽은 작업이 기준 시간 동안 살아 있는 척** — 그동안 같은 대상의 재실행이 막힘

기준 시간을 줄이면 앞쪽이, 늘리면 뒤쪽이 커진다. 정리 시점이 서버 기동이나 다른 요청처럼 작업과 무관한 사건이라는 점도 원인이다.

## 패턴

작업이 끝나는 경우마다 책임자를 나눈다.

| 종료 경우 | 책임자 | 방법 |
|---|---|---|
| 정상 완료·예외 | 실행 주체 | `try/except`에서 직접 `completed`/`error` 마감 |
| 시간 초과 | 실행 주체 | `asyncio.wait_for(run_job(), timeout)`, 마감은 바깥 래퍼에서 (`CancelledError`는 `except Exception`에 안 잡힘) |
| 프로세스 사망 | 상태를 읽는 쪽 | 실행 주체가 작업 행에 주기적으로 `heartbeat_at` 기록, 읽기 직전 조건부 UPDATE로 마감 |

```sql
UPDATE jobs SET status = 'error', finished_at = NOW(), error = 'worker stopped'
WHERE id = $1 AND status = 'running'
  AND heartbeat_at < NOW() - INTERVAL '2 minutes';
```

- 판정은 그 작업 상태를 **읽는 API**(상태 조회, 목록 조회, 같은 대상 새 작업 생성)에서 읽기 직전에 한다. 상태가 의미를 갖는 건 누군가 읽을 때뿐이므로 상주 감시자가 필요 없다. 화면이 진행 중 작업을 폴링하면 사망 후 판정 간격 안에 바로 반영된다
- 조건부 UPDATE라 여러 워커가 동시에 판정해도 한 번만 적용 → "누가 정리 담당인가"를 정할 필요 없음
- 서버 기동 시 시간 기준 일괄 정리는 없앤다 (멀티 워커에서 다른 워커의 정상 작업까지 마감하는 원인)

## 전제 조건

생존 신호를 별도 asyncio 작업으로 찍는다면 **작업 안에 이벤트 루프를 막는 동기 호출이 없어야 한다.** 동기 DB 드라이버·라이브러리 호출이 루프에서 바로 돌면 그동안 신호가 멈춰 살아 있는 작업을 죽었다고 오판한다 → 동기 호출은 `asyncio.to_thread`로 옮긴다. 같은 이유로 `wait_for` 취소도 동기 구간이 끝나야 반영되고, 스레드로 보낸 작업은 취소해도 스레드는 끝까지 돈다(결과만 버림).

## 대안과 비교

- **주기 정리 배치(각 워커에 루프):** DB가 항상 최신이지만 그 루프의 생존을 감시할 코드가 또 필요. API를 거치지 않고 작업 테이블을 직접 읽는 곳(대시보드·통계)이 생기면 그때 추가 검토
- **워커 단위 lease:** 상주 폴링 루프가 있을 때(한 워커만 작업을 가져가는 구조)에 맞음. 요청 워커가 직접 실행하는 구조에서는 판정 대상이 워커가 아니라 작업이라 작업 단위 신호가 맞음

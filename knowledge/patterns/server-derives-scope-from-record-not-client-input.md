# 조회 대상(스코프)은 클라이언트 입력이 아니라 서버가 레코드에서 확정한다

## 문제

멀티 테넌트·멀티 DB 구조에서 "이 요청이 어느 대상(테넌트·시스템·DB)을 조회하는가"를
클라이언트가 요청마다 보내고 서버가 그대로 쓰는 구조는 흔하다. 리소스 id 와
스코프를 함께 받는 형태다.

```
POST /chat
{
  "conversation_id": "conv_abc",
  "metadata": { "system_name": "sales", "connection_name": "conn_a" }
}
```

서버가 이 값을 검증 없이 사용하면 **값을 바꿔 보내는 것만으로 권한 없는 대상을
조회**할 수 있다. 인증(누구인가)은 JWT 로 검증하면서 인가(무엇에 접근 가능한가)는
클라이언트 주장을 믿는 셈이다.

특히 위험한 조합:

- 생성 시점에는 권한을 확인하지만, 이후 요청마다는 확인하지 않는 경우
- 검증된 사용자 정보와 검증되지 않은 클라이언트 입력이 **같은 dict 에 섞여** 하위
  코드로 내려가는 경우 — 소비하는 쪽에서 둘을 구분할 방법이 없다

## 해결 패턴

**리소스 id 만 받고, 스코프는 서버가 그 리소스의 레코드에서 읽는다.**

```
POST /chat  { "conversation_id": "conv_abc" }   ← 스코프 없음

서버:
  conversation_id 로 레코드 조회
    → 소유권 확인
    → 레코드에 기록된 스코프 획득
    → 그 스코프에 대한 현재 권한 재확인
    → 확정된 값을 요청 컨텍스트에 주입
```

핵심 세 가지:

1. **클라이언트 입력을 덮어쓰지 말고 아예 싣지 않는다.** 덮어쓰기(블랙리스트)는 새 키가
   생기면 빠뜨리기 쉽다. "서버가 넣을 것만 넣는다"(화이트리스트)면 그 실수가 구조적으로
   불가능하다. 클라이언트가 정말 보내야 하는 값이 있으면 명시적으로 하나씩 추가한다.

2. **요청마다 재확인한다.** 생성 시 한 번만 확인하면 권한 회수가 반영되지 않는다.
   조회와 권한 검증을 **하나의 쿼리·하나의 함수로 묶으면** 호출부가 검증을 빠뜨릴 수 없다.

   ```python
   # 스코프만 주는 함수와 권한만 보는 함수를 따로 두면 호출부가 후자를 빼먹는다
   async def get_authorized_scope(resource_id, user_id) -> Scope | None:
       # 소유권 + 대상 활성 여부 + 권한을 한 번에 판정
   ```

3. **이름이 아니라 id 로 받는다.** 자연키가 전역 유일이 아니면(예: 부모 단위로만 유일)
   이름 단독 조회는 엉뚱한 대상을 집을 수 있다.

## 진입점을 전부 찾을 것

같은 스코프가 흘러드는 엔드포인트가 하나가 아닌 경우가 많다. SSE·WebSocket·폴링처럼
같은 기능의 변형이 있으면 **전부 같은 규칙을 적용**해야 한다. 한 곳만 막으면 나머지로
우회된다.

공통 헬퍼로 묶어두면 나중에 한 곳만 고치는 사고를 막을 수 있다.

## 부수 효과: 저장된 값을 덮어쓰지 말 것

스코프를 클라이언트에서 받던 구조에서는 요청 값으로 레코드를 갱신하는 코드가
따라붙기 쉽다(`ON CONFLICT DO UPDATE ... SET scope = EXCLUDED.scope`). 이 경우
권한이 회수돼 스코프가 빈 상태에서 요청이 오면 **저장된 값이 NULL 로 덮어써져
영구 유실**된다. 권한을 다시 부여해도 복구되지 않는다.

리소스의 소속은 생성 시점에 확정되는 사실이므로, 이후 갱신 대상에서 제외한다.

## 언제 쓰나

- 하나의 리소스가 특정 대상에 묶이고, 그 대상에 대한 접근 권한이 사용자별로 다를 때
- 대화·문서·프로젝트 등 "컨테이너" 단위로 스코프가 결정되는 모든 구조
